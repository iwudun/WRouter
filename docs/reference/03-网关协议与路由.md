## 0. 全局视图：一次请求走过的三段

```
客户端
  │  ① 入站：协议 → 语义模型（Inbound Adapter 解码）
  ▼
SemanticRequest  ──────────────────────────────────────────────┐
  │  ② 出站：语义模型 → 上游协议（Outbound Adapter 编码）      │
  ▼                                                             │
上游 HTTP（SSE 或 JSON）                                        │
  │  ③ 回程：上游 → 语义事件 → 客户端协议帧（ClientStream）      │
  ▼                                                             │
客户端 ◀────────────────────────────────────────────────────────┘
```

**关键事实**：

- 请求面与非流响应面在「同协议」时真透传（字节保真，不经语义模型）；请求面仅顶层 model 不同时为定点 Patch。
- 流式响应面：原生同协议且执行器为 SSE 时输出上游原字节（Raw + ByteExact）；跨协议、NDJSON→SSE 与 JSON→流合成走 Translate 重建。
- 三条数据面由同一 `plan_exchange` 规划；未知组合在触达上游前拒绝，不回退透传。

> 机制细节见 [design/协议交换.md](../design/协议交换.md)（规划器 / 保真等级 / 无损基座 / 适配器）与 [design/流式状态机.md](../design/流式状态机.md)（上游帧 → 语义事实 → 客户端帧）。

## 2. 协议矩阵

> 本节是协议交换的权威契约（含 file:line）；机制导读与取舍见 [design/协议交换.md](../design/协议交换.md)。

### 2.1 请求面 passthrough 格

权威实现：`wr-domain/src/protocol/mod.rs:399-410`（函数 `upstream_payload_impl_with_report`，`:385-425`）。

```rust
let passthrough = match (source, target) {
    (SourceProtocol::OpenAi, ProviderProtocol::OpenAi) if !native_responses => true,
    (SourceProtocol::OpenAiResponses, ProviderProtocol::OpenAi) if native_responses => true,
    (SourceProtocol::Anthropic, ProviderProtocol::Anthropic) => true,
    (SourceProtocol::Gemini, ProviderProtocol::Gemini) => true,
    (SourceProtocol::OpenAiEmbeddings, _) => true,
    (SourceProtocol::GeminiStream, ProviderProtocol::Gemini) => true,
    _ => false,
};
```

**维度**：客户端入口协议（7 值）× 上游协议（3 值）× `native_responses` 修饰条件。

**语义**：
- `OpenAi × OpenAi` 仅在 **非** native_responses 时透传；
- `OpenAiResponses × OpenAi` 仅在 **是** native_responses 时透传；
- 命中 → `payload.clone()`，**不经语义模型**，报告策略记 `native_passthrough`（`:413`）。

**特例**：`gemini_interactions` 请求走**协议专项 helper**（浅变换 `input` → `contents`，保留其余键），不经语义内核，且**不产报告**（`report = None`）—— `protocol/mod.rs:419-421` → `gemini::interaction_to_gemini(payload)`。

### 2.2 非流响应面 passthrough 格

权威实现：`wr-domain/src/protocol/mod.rs`（函数 `try_decode_response`；失败返回 `ConversionFailure`，生产转发不得回退原对象）。

与请求面**同格同条件**，差异三处：

1. `(GeminiInteractions, Gemini)` 在**响应面为 `false`**（走语义转换），在请求面是协议专项 helper；
2. 响应面同样经 `ensure_combination_supported`（`protocol/mod.rs:584`；请求面在 `:399`，G-7 已关闭）；
3. 命中 → `value.clone()`；未命中 → `semantic::convert_response`，**解码失败回退原值**（`protocol/mod.rs:551+`）。

### 2.2.1 流式响应面：原生 Raw，跨协议 Translate

流式响应先经 `plan_exchange` 固定数据面模式：原生同协议且执行器为 SSE 时，`RecordEncoder` 直接输出上游 `RawRecord` 原字节；跨协议、NDJSON→SSE 与 JSON→流合成仍经 `ClientStream` 重建。

> **边界**：非流客户端 + 流式上游明确不支持（W2-2）；`GeminiInteractions` 仅非流（`stream=true` 在规划层拒绝）。机制见 [design/协议交换.md](../design/协议交换.md) §1/§4；状态机见 [design/流式状态机.md](../design/流式状态机.md)。

### 2.3 `native_responses` 判定

`wr-domain/src/provider.rs:579-587`：

```rust
pub fn serves_openai_responses_natively(&self) -> bool {
    self.protocol == ProviderProtocol::OpenAi
        && self.protocol_style.as_deref().map(str::to_ascii_lowercase).as_deref()
            == Some("openai_responses")
}
```

| `provider.protocol` | `provider.protocol_style`（来自配置 JSON 的 `type` 键） | native? |
|---|---|---|
| `OpenAi` | `"openai_responses"` | ✅ true |
| `OpenAi` | `"openai_chat_completions"` / 其它 / `None` | ❌ false |
| `Anthropic` / `Gemini` | 任意 | ❌ false |

> ⚠️ `protocol_style` **无枚举校验**（`provider.rs:500-504` 取任意非空字符串），只有 `openai_responses` 一值有特殊语义。

**相邻口径**：`provider.rs:595-605`（`effective_wire_protocol()`）—— `openai_responses` → `"openai_responses"`；`openai_chat_completions` → `"openai"`；其余 → `protocol.as_str()`。该值在**请求落库时**写入 payload 键 `provider_protocol`（读取侧现算会随配置漂移，见 `provider.rs:589-594` 注释）。

### 2.6 执行契约摘要（P5 已接线）

> P1–P5 的阶段叙事与实施记录已归档；本节只留当前契约，完整机制见 [design/协议交换.md](../design/协议交换.md)。

**保真等级**（`wr-domain/src/protocol/contract.rs`）：

| 等级 | 承诺 |
|---|---|
| `ByteExact` | 未修改实体正文原字节保留；不承诺 TCP/HTTP chunk、TLS、头字段大小写一致 |
| `StructureExact` | JSON 值、顺序、存在性、身份引用一致；允许声明过的重序列化 |
| `SemanticEquivalent` | 异协议表达不同，但声明支持的内容、行为与生命周期等价 |

**正文模式**：`Raw | Patch | Translate | Unsupported`。同协议原生格 = `Raw + ByteExact`，跨协议 = `Translate + SemanticEquivalent`；`GeminiInteractions→Gemini` 请求面 `Patch`、响应面 `Translate`。表示转换由 `ResponseExecutor`（SSE / NDJSON / JSON / JSON→流合成）按实际可达路径选择；非流客户端 + 流式上游无执行器（W2-2）。

**唯一规划入口**：`protocol::contract::plan_exchange`（`RequestProfile` + 目标协议 + `native_responses`）。未知/不支持组合返回 `ContractViolation`，不回退透传。能力矩阵每项 ∈ `Native | Equivalent | Degraded | Unsupported`：`Refusal`/`MultiCandidate`/`MultiItemPart` = Equivalent，`Annotations` = Degraded，`ReasoningSignature`/多模态/有状态引用 = Unsupported（签名同协议 Raw 保留，跨协议不迁移）。

**无损基座**（`wr-domain/src/wire/`）：`RawRecord`（原字节 + 内容范围/偏移/来源）、`SseFramer` / `NdjsonFramer`（字节级分帧，保留未知字段与 EOF 残片）、`JsonView`（重复键/数值词法/深度显式记录）、`WireLimits`（超限为粘性硬错误）。`Content-Type` 走精确媒体类型匹配，不做子串匹配。

**流式控制链**：`SourceFacts`（一帧只解码一次）→ `SourceObserver`（生命周期/用量/续写投影/重放识别）→ `PreparedExchange`（出站前固定模式）→ `select_response_executor`（响应头后只选已规划执行器）→ `Delivery`（首帧入队前提交 HTTP 头）。`committed_text()` 是断流续写唯一 prefill 来源。详见 [design/协议交换.md](../design/协议交换.md) §7。

**边界**：跨协议签名/多模态/stateful 迁移仍 Unsupported；Interactions 仅 Gemini 上游且仅非流；annotations 仅在 Responses 保留；错误响应仍归一化为客户端协议信封。

### 3.4 `ToolCallId` / `ToolArguments` / `Extensions`

**`ToolCallId`**（`model.rs:405-408`）：`local: String` + `origin: IdOrigin`（`Source` = 原值 / `Regenerated` = 转换层生成，**必须伴随 `RegeneratedId` 诊断**，`model.rs:410-417`）。

**`ToolArguments`**（`model.rs:421-448`）：`Raw(String)`（OpenAI 的 JSON 字符串形态）| `Parsed(Value)`（Anthropic / Gemini 的对象形态）。
- `as_object()` → `(Value, bool 是否降级)`：`Raw` 解析失败返回 `({"raw": s}, true)`，调用方记 `DowngradedContent`（`model.rs:431-439`）。
- `as_raw_string()` → `String`：`Raw` 原样；`Parsed` 序列化（`model.rs:442-447`）。

**`Extensions`**（`model.rs:122-163`）：按 `source` 分块，每块内是 `BTreeMap<String, Value>`。
- `insert(source, key, value)`（`:136-147`）：同名 `source` 复用同一 block；**同名键多来源不合并、全部保留**。
- `source` 的含义：来源协议/提供方命名空间（`"openai"` / `"anthropic"` / `"gemini"`）。

## 7. 流式响应面（核心）

> 完整状态机、快照对账与聚合预算见 [design/流式状态机.md](../design/流式状态机.md)。本节只留数据流、收口契约与两张冻结映射表。

### 7.1 数据流

```
上游字节 → SseFramer / NdjsonFramer 分帧 → SourceFacts（一帧只解码一次）
→ SourceObserver（生命周期 / 用量 / 续写投影）→ ClientStream（目标编码）→ Delivery（首帧入队前提交 HTTP 头）
```

- 背压 `mpsc::channel(8)`；客户端断开 → body drop → 终止并记 **499**。
- 响应头已发后 **HTTP 状态恒 200**，错误一律走 SSE 信封；原生 Raw 路径由 `RecordEncoder` 直接输出原字节，不经 `ClientStream`。
- 语义泵每候选构造一次；聚合请求回写实际输出 model。

### 7.2 四个客户端状态机的收口契约

| 实现 | `finalize` | `finalize_incomplete` |
|---|---|---|
| `ChatClient` | 上游已给 `finish_reason` → 不补第二个，只补未下发的 usage 尾块（`choices: []` + usage，不带 finish_reason）+ `[DONE]`；未给 → 兜底 `"stop"` | 不适用 |
| `AnthropicClient` | `flush_start` → 关闭所有未闭合块 → `message_delta`（`stop_reason` 取语义 Finish；缺失回退 `tool_use`/`end_turn`）→ `message_stop`，整条流只输出一次终结序列 | 不适用 |
| `ResponsesTargetClient` | 关闭打开中的 item → 补齐终态快照里未输出的 item → `response.completed` 或 `response.incomplete` → `[DONE]` | 同一收口路径但 `force_incomplete`：先收口 item（断流前内容必须进 output）→ `response.incomplete`（`incomplete_details.reason="upstream_stream_incomplete"`）→ `[DONE]`；**不合成成功** |
| `GeminiClient` | **不产出终结序列**：只 flush 尚未输出的工具调用（参数完整才发 `functionCall`）；`finishReason` 只由上游 `Finish` 帧触发，缺失则流由 EOF 截断 | 不适用 |
| `Passthrough` | 空；原字节由管线直出 | 不适用 |

共同约束：**一条流只能有一个终止字段，且沿用上游真实取值**；兜底默认值只在上游完全没给时补。收口帧序与逐状态机行号见 [design/流式状态机.md](../design/流式状态机.md) §3。

### 7.3 终止字段唯一性（2026-11-05 契约）

一条流里**只能有一个**结束原因（`finish_reason` / `stop_reason` / `finishReason`），且**沿用上游真实取值**（不按「有 tool_calls 否则 stop」降级）。客户端状态机记住上游给过的结束原因，收尾只补不含终止字段的尾块 + 哨兵；上游没给才兜底。

> 历史缺陷：旧 `ChatClient` 收尾无条件补硬编码 `finish_reason:"stop"`，与上游 `tool_calls` 构成两个不同值 → 严格客户端判 `conflicting_finish_reason` 拒绝整条流。回归：`chat_client_emits_single_finish_reason_for_tool_calls`、`streaming_emits_single_finish_reason_matching_upstream`。同族教训见 `docs/LESSONS.md` L-024。

### 7.4 上游事件 → 语义事件映射（Responses，冻结）

实现：`wr-domain/src/semantic/stream/decode/responses.rs`（`decode_responses_upstream`）；事件名取自 SSE `event:` 行优先、其次 payload `type`。

| 上游事件 | 语义事件 |
|---|---|
| `response.created` / `response.in_progress` | `MessageStart { id, model }` |
| `response.output_item.added` + `function_call` | `ToolCallStart` |
| `response.output_item.added` + `reasoning` | `ReasoningStart` |
| `response.output_item.added` + `message` | `PartStart { part: Text{""} }` |
| `response.output_item.added` + 其它 type | 无事件 |
| `response.output_item.done` | `Opaque{raw}` + `ItemSnapshot` + `ItemEnd`（不推第二次 `ToolCallStart`） |
| `response.content_part.added` | part 带**非空** text 时推 `PartDelta`；空文本不推 |
| `response.content_part.done` | 不推事件（全文仅作校验） |
| `response.output_text.delta` | `PartDelta` |
| `response.output_text.done` | `PartEnd` |
| `response.reasoning_summary_part.added` | `ReasoningStart` |
| `response.reasoning_summary_text.delta` | `ReasoningDelta` |
| `response.reasoning_summary_text.done` / `reasoning_summary_part.done` / `function_call_arguments.done` | `PartEnd` |
| `response.function_call_arguments.delta` | `ToolArgumentsDelta` |
| `response.completed` | `Usage` + `Finish{Stop}` + `StreamEnd{incomplete:false}` |
| `response.incomplete` | `Usage` + `Finish{按 incomplete_details.reason 映射}` + `StreamEnd{incomplete:true}` |
| `response.failed` / `error` | `Error` |
| `response.cancelled` | `StreamEnd{incomplete:true}` |
| 其它未识别事件 | `Opaque{raw}`（不吞事件） |

> **收口帧不是内容帧**（`docs/LESSONS.md` L-029）：done 帧只收口，不重发内容；正文仅校验不回填。

### 7.5 Responses 客户端分槽与 opaque（摘要）

客户端 `output_index` 由 `next_output_index` **单调自分配**，与上游 `output_index` 解耦，映射只经 `item_for_key`；added / delta / done 由 started/done 守卫保证幂等。opaque 只转发 `raw.type` 以 `response.` 开头的事件，异协议 opaque 不冒充。详见 [design/流式状态机.md](../design/流式状态机.md) §4。

### 7.6 工具参数对账（摘要）

`reconcile_arguments(committed, snapshot)` 只有四种结论：`Duplicate` / `Extension{suffix}` / `Snapshot{arguments}`（原本为空）/ `Conflict{committed,snapshot}`。`ToolCallAssembly` 只允许快照延长**已提交前缀**；冲突保留已提交前缀，不拼出非法 JSON。`ClientStream` 账本存**已接收参数全文**，done 帧只补后缀或（账本为空时）补整段。详见 [design/流式状态机.md](../design/流式状态机.md) §5。

### 7.7 StreamAggregator（摘要）

幂等键 = 工具调用 id；`PartStart` 赋值覆盖、`PartDelta` 对文本追加；`Parsed` 空占位整体替换不拼接；`with_budget(max_bytes)` 超限置 `suppressed` 并停止累积，调用方不写缓存。详见 [design/流式状态机.md](../design/流式状态机.md) §6。

### 7.8 合成 vs 解码

| 函数 | 方向 | 场景 |
|---|---|---|
| `response_to_events` / `response_to_updates` | 语义响应 → 事件 / 层级更新 | Chat/Anthropic/Gemini 与 Responses 目标编码 |
| `synthesize_client_frames` | 语义响应 → 客户端 SSE 帧 | 客户端流 / 上游非流 |
| `synthesize_client_response_frames` | 客户端 JSON → 客户端 SSE 帧 | 缓存重放 / JSON→流合成 |

生产流、合成、缓存重放共用 `ClientStream` 一组目标状态机；不存在第二套帧生成器。详见 [design/流式状态机.md](../design/流式状态机.md) §7。

`execution_plan.rs:59-113`：`off`/无请求体 → 1 个 attempt；`retry` → `retry_count+1` 个同一 primary（clamp `[0, 9999]`）；`model-chain` → `primary + fallback.models` 保序去重后逐个解析。全局 fallback 是唯一回退来源。机制见 [design/选路与候选计划.md](../design/选路与候选计划.md) §7。

### 9.3 聚合展开

`model_groups.rs:111-138`：targets 过滤 enabled → 按 `(priority ASC, 配置顺序)` 稳定分层；`first` 层内全保留；`weighted` 每层加权抽一个（层权重和 ≤0 取首）；`sticky` 命中置顶并剔除同 provider 其余目标（提前返回，不再分层）。健康门过滤后产出候选；全部不可用返回空候选 + 明确错误串，**不回落全池**。详见 [design/选路与候选计划.md](../design/选路与候选计划.md) §5。

## 10. 韧性层

> 完整机制、常量与逐状态行为见 [design/韧性与凭据.md](../design/韧性与凭据.md)；本节只留入口与摘要。

- **三层重试**：计划 attempts → 候选链 → 同 provider 原地重试；总预算 `reliability.retryBudget` 默认 16（下限 1）跨三层共用，每次出站扣 1。入口 `forward/json.rs:916`（非流）/ `forward/stream.rs:599-629`（流式）。
- **码集**：可重试 `[408,409,429,500,501,502,503,504]` 与网络哨兵 `status==0`；不重试 `[400,401,403,404,422]`。`should_fallback_mode`：`status < 400` 不回退；`model-chain` 任意 ≥400 可回退。401/403 换候选不终态；404/422 终态；501 可重试但不进熔断。
- **退避**：`backoff = min(1s·2^n, 30s)`，抖动 ×`[0.5,1.5)`；`Retry-After` 分支夹 `[1,60000]ms`；429 且 `Retry-After > 60s` 跳过原地重试直接换候选。
- **熔断**：`Closed/Open/HalfOpen` 三态；默认计票集 `[408,429,500,502,503,504]`（不含 501）；只做候选过滤，无「熔断即 503」分支。
- **并发**：每 provider 信号量，默认 `max_in_flight=8`；`queue_timeout_ms=0` 槽满即 429，`>0` 排队超时 429；退避前 drop 许可、醒后重取。
- **限流**：固定窗口（非滑动），键 `{identity}:{scope}:{metric}:{window_start}`；限流不回滚、预算超支回滚。
- **凭据池**：失败语义分类 → 冷却时长/作用域；账号级 vs 模型级；确定性抖动 `min(时长/5, 30s)`；`first/pinned/weighted/balanced/sticky` 五策略；全冷却探最早恢复。

### 11.2 合并语义

- `merge_max(&mut self, other)`（`:30-40`）：逐计数器取 **max**；`total_tokens` = `max(旧total, 新total, input+output)`。理由（模块文档 `:3-6`）：上游 usage 事件是**累计快照**，重复终态块不得重复计数。
