# 02 · 架构设计

> 最后核验:2026-11-07。描述当前 Rust 后端 + React 前端 + Tauri v2 桌面壳的实际架构;行为约定与历史决策见 planning 归档。

## 1. 进程模型与启动协议

Windows 桌面形态下运行时只有**一个进程**:Tauri 壳内嵌后端 runtime(后端**同进程**,不再 spawn 子进程)。

```
Tauri 壳(wrouter-desktop.exe)
  ├─ webview 加载 http://127.0.0.1:3462/(生产)/ vite dev server(dev)
  └─ 后端 runtime(独立线程 + 独立 tokio runtime,与壳同进程)
        ├─ 监听 3460(gateway)与 3462(admin),同进程双端口
        │    └─ 3460 可单独暂停/恢复,3462 管理面始终在线
        └─ 壳退出时用 watch 广播停机信号,后端随之收尾
```

- **没有后端子进程**:`wr-server` 以 path 依赖进壳,跑在壳内的独立线程 + 独立 tokio runtime 上;进程表里只有壳。Linux 的纯后端形态仍是独立的 `wr-backend` 单二进制。
- dev 模式(`npm run dev`):`scripts/dev.mjs` 起 vite dev server → `cargo run --manifest-path desktop/src-tauri/Cargo.toml`,壳经 `WROUTER_VITE_DEV_URL` 指向 vite。
- 前端加载:开发态加载 Vite dev server(HMR);打包态加载管理面 `http://127.0.0.1:3462/`(D5,后端静态托管同一份 `frontend/dist`)。
- 前端与后端通信:壳在页面脚本前注入 `window.wr`(8 个桌面方法),业务方法由 `web-client-bridge.ts` 就地补齐,内部用 fetch 调 `x-wrouter-web-auth` 鉴权的管理面接口(见 §5)。
- 纯后端形态:`wr serve` 直接运行(无桌面壳),Linux 下由 systemd 用户服务(`packaging/wrouter.service`)管理。

## 2. Rust 后端分层

```
backend/crates/
├── wr-cli          CLI 入口:wr serve / version / doctor 子命令;[[bin]] 名为 wr
├── wr-server       axum 装配:双端口 serve、gateway/admin 路由、鉴权、SSE、维护任务
├── wr-app          应用层端口 trait(config_store / breaker_health_store / idempotency_store 等)
├── wr-domain       纯领域层:路由决策、协议模型、重试/回退/熔断判定、日志策略
├── wr-infra        基础设施:SQLite、配置读写、上游 HTTP 客户端、出站代理、MITM CA
└── wr-test-utils   跨 crate 测试工具(仅 dev-dependency)
```

依赖方向:`wr-cli → wr-server → wr-app(trait)← wr-infra(实现)`,领域逻辑全部下沉 wr-domain。

**wr-domain 纯度守护**:`scripts/check-rust.sh` 用 grep 强制 wr-domain 的 Cargo.toml 不得出现 `tokio | axum | reqwest | rusqlite | hyper | tower`——领域层不允许知道具体 IO 框架,保证业务规则可独立测试与移植。

版本注入:后端版本由构建期 `WR_VERSION` 环境变量传入(打包脚本从根 package.json 读取),不写 Cargo.toml。

## 3. 请求生命周期(gateway)

```
客户端(3460)
  → 路由匹配(lib.rs 路由表,见 03 §1)
  → 协议处理器(openai chat / anthropic messages / gemini / responses / embeddings)
  → 模型名解码与路由决策(wr-domain/src/routing/:规则引擎 → Provider 选择 → 执行计划)
  → 重试/回退包裹(同 provider 重试 → 候选链回退 → 执行计划 attempts,见 03 §4)
  → 上游转发(wr-infra HTTP 客户端;SSE 流式逐事件透传,tool_call 片段重组)
  → 可观测性记录(wr-domain/src/observability/:request_logs 元数据 + 可选正文)
```

- 所有入站路径默认 `DefaultBodyLimit::max(64 MiB)`(`WROUTER_MAX_BODY_BYTES` 可调),超出在读取阶段返回 413。
- 失败判定与重试码集中在 `wr-domain/src/gateway.rs`(`should_retry` / `should_fallback_mode`);Python parity 已随 Python 后端退役(R7),现行基线是 golden replay 的 Rust 行为快照。
- 后台维护:`wr-server/src/gateway/maintenance.rs` 的 LogMaintenanceService 定期清理过期日志正文(见 §6)。

## 4. 存储层

单库 **`<data_dir>/config.sqlite`**,建表用 `CREATE TABLE IF NOT EXISTS` 原地扩容,无 migration runner(`wr-infra/src/sqlite/schema.rs` 的 `TABLES` 常量是唯一权威清单,**18 张表**):

| 表 | 用途 |
|---|---|
| `app_config` | 应用配置(JSON) |
| `secrets` | Provider api_key 等敏感值,独立于配置存储,管理接口只回脱敏值 |
| `metadata` | 杂项元数据(含首启标志等) |
| `provider_health` | Provider 健康探测结果 |
| `provider_accounts` | Provider 账户快照 |
| `account_snapshots` | 账户用量快照历史 |
| `circuit_breaker_state` | Provider 熔断状态 |
| `idempotency_entries` | 幂等键 |
| `request_logs` | 请求日志元数据(永久保留,默认) |
| `request_log_attempts` | 每次上游尝试一条(request_id + ordinal):上游请求/响应、响应头、转换报告 |
| `request_log_bodies` | 请求/响应正文(默认不捕获,开启后 7 天过期) |
| `request_log_headers` | 请求头快照(随正文捕获开关) |
| `request_log_trace` | 协议转换诊断 trace(kind + payload) |
| `usage_rollup` | 用量小时卷积(维度:模型/上游模型/请求模型/Provider/客户端/api_key) |
| `usage_rollup_hist` | 用量分位数直方图(同维度同小时桶 + metric + bucket):TTFT / 吞吐的 P50、P95 |
| `savings_events` | 成本节省事件(每请求一行,kind = compression / response_cache) |
| `response_cache` | 响应缓存磁盘层(内存 LRU 之外的二层) |
| `model_fingerprint` | 用户自建模型指纹库(L2 全局候选 / L3 供应商锚点) |
| `model_fingerprint_samples` | 指纹探针样本(重拟合需要原始样本,故单独成表) |

密钥三态语义(不可回退,动密钥代码前必读):`saveApiKeys`/`save_config` 中**缺失、空串或 `***` 均不改现有密钥;显式 `null` 才清空**;其余值为 upsert。

## 5. 管理面(admin,端口 3462)

REST + RPC + SSE 三种接口同进程同端口(`wr-server/src/admin/mod.rs`):

**免认证**:`GET /api/v1/health`、`GET /api/v1/capabilities`。

**需认证**(`x-wrouter-web-auth` 头,不匹配返回 401;token 来源优先级:`WROUTER_WEB_AUTH_TOKEN` 环境变量 > `<data_dir>/auth_token` 文件,后者首次启动自动生成):

| 路由 | 方法 | 说明 |
|---|---|---|
| `/api/wr/rpc` | POST | 统一管理 RPC(30 个方法,下表) |
| `/api/wr/events` | SSE | 实时事件推送(状态/日志/用量变化),管理面轮询已退役 |
| `/api/v1/config` | GET / PUT | 读/写配置 |
| `/api/v1/config/export`、`/config/import` | GET / POST | 配置导出/导入 |
| `/api/v1/status`、`/api/v1/metrics` | GET | 运行状态 / 指标 |
| `/api/v1/providers` | GET | Provider 列表 |
| `/api/v1/providers/{id}` | PUT / DELETE | 建/改/删 Provider |
| `/api/v1/providers/probe`、`/providers/health`、`/providers/health/check` | POST/GET/POST | 连通性探测/健康查询/全量探测 |
| `/api/v1/request-logs`、`/api/v1/usage` | GET | 日志查询 / 用量统计 |

**30 个管理 RPC 方法**(`wr-server/src/admin/config.rs` 为权威定义):

`getConfig` `saveConfig` `saveApiKeys` `getGatewayStatus` `getAppInfo` `checkProviderConnectivity` `getProviderAccountSnapshots` `probeProviderCandidates` `fetchProviderModels` `testApiEndpoints` `testProxyPreset` `getUsageStats` `getApiKeyLastUsed` `getRequestLogDetail` `getRequestLogTrace` `getCallLogs` `exportData` `getUpdateStatus` `getProviderCredentialStats` `clearCredentialCooldown` `getSavingsStats` `detectModelFingerprint` `listModelFingerprints` `enrollModelFingerprint` `deleteModelFingerprint` `exportModelFingerprints` `importModelFingerprint` **`getRuntimeControl`** **`setGatewayEnabled`** **`stopService`**

另有 4 个 desktop-only 占位(openExternal / updateCheck / updateDownload / updateInstall,Web 模式 501)。

### 5.1 服务控制

后端把「暂停 / 恢复 / 退出服务」做成**通用能力**(所有运行时都有,不限 Linux + 浏览器):

| RPC | 语义 |
|---|---|
| `getRuntimeControl` | 自报托管方式与可执行动作:`managedBy`(`embedded`/`process`/`systemd`)、`canPause`、`canExit`、`exitAction`、`restartHint`、`gatewayState`、`stopping`(停机已受理但进程尚未退出) |
| `setGatewayEnabled(enabled)` | **暂停/恢复网关面(3460)**:暂停 = 关闭 3460 监听(不占端口、不转发;客户端 connection refused),**管理面 3462 不受影响**,页面保持可用 |
| `stopService` | **优雅停机整进程**(仅 `managedBy != embedded`):先回响应(仅代表**已受理**),约 1.2s 后停机,退出码 0 → systemd `Restart=on-failure` 不再拉起 |

- 控制通道是 `ServiceControl` 的五路 `watch`;网关面是独立任务,暂停态也必须盯停机信号(否则「先暂停再停机」永不退出)。
- **顺序停机**:网关面先收尾(≤10s),管理面在排空期继续在线并如实报 `stopping=true`(自身排空上限 5s,从停机开始计时),等待网关面上限 12s。三个上限都只在停机开始后计时。
- **管理面意外结束 = 整进程停机**(桌面壳弹窗退出);管理面 SSE 停机时补发 `service-stopping` 帧再收流;收尾(落日志 → WAL checkpoint → 关库)无条件执行。
- `embedded` 模式拒绝 `stopService`(正确动作是关窗口,壳退出时后端随之停机);systemd 单元显式声明 `WROUTER_MANAGED_BY=systemd`。

> 状态机、五路通道、三个上限与回归测试见 [design/服务生命周期.md](../design/服务生命周期.md);用户操作语义见 [07 §1.5](./07-FAQ与已知限制.md)。

**三方一致性守护**:上述方法白名单同时维护在 `contracts/wrouter-capabilities.json`、后端 dispatch、`desktop/src-tauri/src/bridge_core.rs`(Tauri 桥接层);`node scripts/validate-capabilities.mjs` 校验三者一致,不一致即质量门失败(另含「前端业务桥 ⊆ JSON」子集检查)。**增删 RPC 必须五点同步**(第五点为 `frontend/src/types/desktop.d.ts`/`web-client-bridge.ts`),清单见方案归档原 11。

**管理面托管前端 SPA**:静态资源由后端静态托管提供 —— Windows 安装态在 `<安装目录>\frontend`,Linux 在 `/usr/share/wrouter/frontend`;浏览器联调直接打开 `http://127.0.0.1:3462/`(同源 `/api/wr/session` 自动取令牌,非 loopback 时用 `?wr_web_token=<token>`)。

## 6. 日志数据策略

`wr-domain/src/observability/log_policy.rs`:

| 数据 | 默认策略 | 可调 |
|---|---|---|
| 请求日志元数据 | 永久保留 | `WROUTER_LOG_RETENTION_DAYS`(0=永久) |
| 请求/响应正文 | **不捕获**(`captureBodies=false`) | 设置页开启;保留期默认 7 天(`WROUTER_BODY_RETENTION_DAYS` 或 `observability.bodyRetentionDays`) |

LogMaintenanceService 后台定期执行 `prune_logs` 落实过期删除；`callLogs` 视图只受正文捕获开关门控。04 §4 已合并到本节(唯一权威表)。

## 7. 前端架构(frontend/)

- **构建**:Vite 8 + @vitejs/plugin-react;**Tailwind 4 是唯一样式系统**(baseui/styletron 已于 F3 清零);依赖仅 @tanstack/react-query、clsx、lucide-react、motion、react(-dom)、recharts、tailwind-merge。
- **数据层**:React Query + SSE 事件流(F2b 起管理面全部实时化,HTTP 轮询退役);语言 i18n(zh/en/system,`pages/home/shared/i18n/`,偏好存 localStorage `wr.ui.language`)。
- **结构**:`src/pages/home/` 下按视图组织——`components/{dashboard,providers,settings}` + 顶层视图组件(api-keys / call-logs / networking / routing / update / layout / dialog-stack / feedback)+ `hooks/`(每视图一个 state hook)+ `shared/`(i18n、类型、日志/路由/用量工具)。
- **日志面板 worker 化**(F4):`components/shared/log-body-{core,worker,client}.ts` 三件套——大 JSON 正文在 Web Worker 内解析/聚合,主线程只收视图元数据,懒加载子节点;`?worker&inline`(file:// 下 URL worker 不可用,必须内联);无 Worker 环境同步回退,行为一致。
- **性能约定**:列表行级 memo + 显式比较器(providers 拆分后);recharts 懒加载;首屏 index chunk ~100KB 量级。

## 8. 桌面壳(desktop/src-tauri/)

Windows 侧唯一桌面壳(Tauri v2);Linux 侧无桌面壳(纯后端 + systemd)。原 Electron 壳已退场,`electron/` 目录已删除。

| 模块 | 职责 |
|---|---|
| `src/main.rs` / `src/lib.rs` | 入口:插件注册、命令注册、起后端、建窗口、启动对账、退出时停机 |
| `src/backend.rs` | 后端同进程(独立线程 + 独立 tokio runtime)与数据目录约定 |
| `src/bridge.rs` | 8 个桌面命令的 Tauri 实现(`window.wr` 的跨运行时公共面) |
| `src/bridge_core.rs` | 纯逻辑:桌面方法清单(`DESKTOP_METHODS`)、注入脚本、URL 白名单 |
| `src/shell_window.rs` / `src/shell_core.rs` | 自绘标题栏的窗口命令与纯逻辑(含 `wr_window_apply_theme` 配色同步) |
| `src/autostart.rs` / `src/config.rs` | 开机自启(OS 登录项)与后端配置读取 |
| `src/http.rs` | 壳内的 HTTP 辅助逻辑 |
| `permissions/desktop.toml`、`capabilities/default.json` | Tauri v2 命令授权(capability 白名单) |

架构要点:

- **进程模型**:一个进程(壳)内跑前端 webview + 后端 runtime。进程表里只有壳,没有后端子进程。
- **窗口加载管理面**:生产 `http://127.0.0.1:3462/`(后端静态托管同一份 `frontend/dist`);dev 加载 vite dev server。
- **桥接层**:壳在页面脚本前注入 `window.wr`(`runtime:"desktop"` + 8 个桌面方法),
  前端 `web-client-bridge.ts` **就地补齐** 28 个业务方法(不覆盖壳注入的值)。
- **窗口控制走独立命令通道**(`wr_window_*`):8 个 `desktopMethods` 是跨运行时公共面,
  窗口控制是壳层 chrome → 不进 `window.wr`,契约不变。
- **自绘标题栏**(Windows):Tauri v2 无 `titleBarOverlay` 等价 API → `decorations(false)` 去系统标题栏,
  前端自绘 min/max/close;拖拽区用 `data-tauri-drag-region`(非 `-webkit-app-region`)。
- **数据目录**:Windows `%APPDATA%\WRouter\data`、Linux `~/.wrouter`;开发态与发布态共用同一路径,`WROUTER_DATA_DIR` 可覆盖。
- **运行日志**:壳启动时初始化 tracing 与 panic 钩子,同时写 stdout 和 `<日志目录>/backend.log`(5MB 轮转 ×9);Linux 纯后端形态由 systemd journal 收集。
- **随包资源**:前端 SPA 与能力契约由 `bundle.resources` 装到安装目录,壳在启动时用
  `WROUTER_FRONTEND_DIR` / `WROUTER_CAPABILITIES_FILE` 指给后端(后端默认路径指向
  源码树,干净机器上没有 → 必须显式指过去)。
- **IPC 授权**:窗口加载的是**远程 URL** → Tauri v2 按 capability 的 `remote.urls`(URLPattern glob)授权,
  未列来源调不动任何命令。

详见 `desktop/README.md` 与内部方案《Electron 迁移 Tauri 可行性与架构方案》（不随开源仓库发布）。
