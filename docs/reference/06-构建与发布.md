# 06 · 构建与发布

> 最后核验:2026-11-07。当前交付**两个平台**:Windows NSIS(Tauri v2 桌面壳)+ Linux RPM(纯后端)。打包命令与容器细节的另一权威来源是 [packaging/README.md](../../packaging/README.md)。
>
> - **后端形态**:安装包内后端唯一形态是 Rust 单二进制 `wr-backend(.exe)`(cargo 构建 `wr-cli`,musl 静态轨入 Linux 包)。
> - **Linux**:纯后端(单二进制 + 前端 SPA + systemd 用户单元,无 GUI 依赖栈),RPM 走 `rpmbuild` + 手写 `packaging/wrouter.spec`;**AppImage 已下线**(纯后端无对应形态)。
> - **Windows**:Tauri v2 桌面壳产出 NSIS 包(自绘标题栏 + 单实例 + 开机自启 + 标题栏配色随主题同步);**Electron 壳已退场**(`electron/` 已删除)。
> - **工具链**:VS Build Tools 2022 17.14.44 / MSVC 14.44.35207 / Windows SDK 10.0.26100.0 / `rustup target add x86_64-pc-windows-msvc` / `@tauri-apps/cli` 2.12.4(装在 `desktop/`)—— 桌面壳默认 target 即 msvc(`desktop/src-tauri/.cargo/config.toml`)。
> - **NSIS 工具链需先预置**:`packaging/fetch-tauri-nsis.ps1`(Tauri 默认从 github.com 下载,本机 github.com 不达;脚本走镜像 + SHA1 校验)。
> - **Linux 产物在 glibc 2.28 基线的验证口径**:RPM/systemd 两层冒烟(`packaging/smoke-test-{linux,systemd}.sh`);musl + gnu.2.28 双轨的四步冒烟脚本(启动/流式转发/管理页/落库)已随归档清理从工作区移除,需要时从 git 历史取回。

## 1. 产物概览

| 平台 | 文件名示例 | 大小 | 构建工具 | 耗时(缓存后) |
|---|---|---|---|---|
| Windows | `WRouter_0.2.3_x64-setup.exe` | 15.43MB | **Tauri v2 CLI (NSIS)** | ~3 min(首次含 NSIS 工具链预置) |
| Linux RPM | `wrouter-0.2.3-1.el8.x86_64.rpm` | 9.57MB | **rpmbuild + 手写 spec** | ~1 min |

产物统一输出 `build/dist/release-v<版本>/`,多平台共用同一目录(版本取自根 `package.json`)。

> 体积对比:Windows 安装包在 Electron 时代是 **154.6MB**,Tauri NSIS 是 **15.43MB**(-90%);Linux RPM **9.57MB**,依赖只有 `systemd` + `/bin/sh` + `rpmlib`(**无 glibc**)。

安装包内部结构:

```
Windows NSIS 安装后: <安装目录>\
├── wrouter-desktop.exe              # 桌面壳(后端同进程)+ VC 运行库
├── uninstall.exe                    # NSIS 卸载器
├── frontend/                        # 前端 SPA(bundle.resources 带出)
└── wrouter-capabilities.json        # 管理面能力契约(bundle.resources 带出)

Linux RPM 安装后(纯后端):
/usr/bin/wr-backend                                   # 单 musl 静态二进制
/usr/share/wrouter/frontend/                           # 前端 SPA
/usr/share/wrouter/contracts/wrouter-capabilities.json # 管理面能力契约
/usr/lib/systemd/user/wrouter.service                  # systemd 用户单元
```

> Windows 侧:壳启动时把 `WROUTER_FRONTEND_DIR` / `WROUTER_CAPABILITIES_FILE` 指向上面那两个随包资源 —— 后端默认路径指向**源码树**(编译期常量),干净机器上没有 → 不指就托管不到 SPA。

数据目录(升级/卸载不丢):Windows `%APPDATA%/WRouter/data/`;Linux `~/.wrouter/`(systemd 服务、纯后端、手跑后端统一 —— TD-ARCH-002)。

## 2. 构建环境

### Windows 构建主机

| 依赖 | 版本 | 用途 |
|---|---|---|
| Node.js / npm | ≥ 20(推荐 22)/ ≥ 10 | Tauri CLI + vite 构建 |
| rustup / rustc | **1.98.0**(`backend/rust-toolchain.toml` 锁定) | 后端 cargo 构建 |
| VS Build Tools 2022 + MSVC target | — | 桌面壳(target `x86_64-pc-windows-msvc`) |
| WinLibs MinGW | 最新(windows-gnu 宿主) | 后端 workspace 的 dlltool/as,构建脚本自动发现 |
| PowerShell | ≥ 5.1 | 构建脚本执行 |
| Docker Desktop | 任意 | 仅 Linux 构建需要 |

### Linux 构建容器

镜像 `wrouter-linux-builder:v2`:Rocky Linux 8.10(glibc 2.28 基线)+ Node 22 + rpm-build 4.14.3 + GCC 13。容器内**只跑 rpmbuild**(不需要 electron-builder / GUI 依赖栈);Rust 二进制由宿主侧 cargo-zigbuild 交叉编译后注入。自定义镜像:`WROUTER_BUILDER_IMAGE=<tag> npm run build:linux`。

> **构建镜像为跨应用共享资产 —— 禁止删除 / 裁剪 / 重建**(见 AGENTS.md)。镜像内**无 nfpm**,故 RPM 走 `rpmbuild -bb` + 手写 spec。

**Windows 上触发 Linux 构建要在 Git Bash 里跑** `packaging/build-linux.sh`(继承 Windows PATH,docker 才能命中 Docker Desktop CLI)。`scripts/build.mjs` 会**自动探测 Git Bash**(从 `git.exe` 反推 `<GitRoot>\bin\bash.exe`,再查常见安装路径),可用 `WROUTER_BASH` 显式指定 bash.exe;探测不到就回落到 PATH 上的裸 `bash` 并打印警告 —— Windows 的 `System32\bash.exe` 是 WSL,默认没有 docker CLI。

### 网络与镜像

| 资源 | 推荐源 |
|---|---|
| Tauri NSIS 工具链 | 从 github.com 下载(本机不可达)→ `packaging/fetch-tauri-nsis.ps1` 走镜像 + SHA1 校验预置到 `%LOCALAPPDATA%\tauri\NSIS` |
| npm 包 | npmjs 直连 |

Linux 构建链路无外网下载(无 appimagetool / 无 fpm / 无 Electron zip)→ 容器内全程离线。

## 3. 一键构建

```bash
npm run setup            # 前置:依赖就绪
npm run build:win        # Windows .exe(NSIS),默认不签名
npm run build:win:sign   # 带签名(需有效代码签名证书)
npm run build:rpm        # Linux .rpm(Docker 容器,纯后端)
npm run build:linux      # 同 build:rpm(Linux 只有 RPM 一个目标)
npm run build:all        # Windows + Linux 一次构建
```

Linux 只有 RPM 一个产物,`build:rpm` 与 `build:linux` 等价(AppImage 已下线)。

构建流程(`scripts/build.mjs`):

```
前置检查(node_modules、version:check)→ 解析版本号生成 `release-v<版本>` 目录
├─ Windows:图标+build-info → scripts/build-desktop.mjs:预置 NSIS 工具链 → 注入 WR_VERSION
│           → tauri build --target x86_64-pc-windows-msvc
│             (beforeBuildCommand 先 vite 构建前端 → cargo 构建壳 → NSIS 打包)→ 拷回产物
└─ Linux:  检查 Docker/镜像 → 宿主侧 build-info + cargo-zigbuild 交叉编译后端 + vite 构建前端
            → packaging/build-linux.sh 容器内:装配 stage(ext4 /tmp,避开 NTFS rename bug)
              → rpmbuild -bb → 拷回产物 build/dist/release-v<版本>/
```

## 4. 安装器配置要点

NSIS(`desktop/src-tauri/tauri.conf.json` → `bundle.windows.nsis`):`installMode: currentUser`(per-user 免管理员)、`languages: [SimpChinese, English]` + `displayLanguageSelector`、`startMenuFolder: WRouter`、`installerIcon`/`uninstallerIcon`。
- **随包资源**:`bundle.resources` 带出 `frontend/dist` 与 `contracts/wrouter-capabilities.json`(壳启动时指给后端,见上)。
- **桌面快捷方式**:Tauri 的 NSIS 模板默认只建开始菜单快捷方式;`packaging/wrouter-nsis-hooks.nsh` 用 `NSIS_HOOK_POSTINSTALL` 补一个桌面快捷方式,`NSIS_HOOK_PREUNINSTALL` 删掉。
- **VC 运行库**:`bundle.windows.bundleVCRuntime: true` → 干净机器没有 VC redist 也能启动。
- **签名**:走 `bundle.windows.certificateThumbprint` / `digestAlgorithm`(命令行 `--sign` 已退化为提示)。
- **卸载**:只清程序文件/快捷方式/注册表,**保留用户数据目录**。
- **安装目录**:干净机默认 `%LOCALAPPDATA%\WRouter`(per-user);静默安装可用 `/S /D=<绝对路径>` 改目录。
- **升级会沿用旧目录**:NSIS 把上次安装目录记在 `HKCU\Software\wrouter\WRouter`(卸载器**不删**这个键),下次安装直接装回该目录。→ **从旧 Electron 版升级时,建议先卸载旧版再装新版**,否则新壳会装进旧目录、且旧 Electron 文件会残留占空间。

**RPM(P2 改为手写 spec `packaging/wrouter.spec`)**:
- `AutoReq: no` + 显式 `Requires: systemd` / `/bin/sh` → 实际依赖只有 `systemd`、`/bin/sh` 与 `rpmlib` 系列,**无 glibc**,麒麟 V10 / UOS / CentOS 7 等老系统可装;
- systemd 用户单元由 `%files` 直接拥有(`/usr/lib/systemd/user/wrouter.service`)→ 卸载时随包删除;
- `%post` / `%preun` 调 `/usr/libexec/wrouter/after-{install,remove}.sh`(只打印提示 / 尽力停服务;
  root 上下文无用户会话,无法代用户 `systemctl --user`);
- 载荷:`/usr/bin/wr-backend`(musl 静态)、`/usr/share/wrouter/frontend/`、`/usr/share/wrouter/contracts/`。

图标:`frontend/src/assets/logo.png` → `packaging/build-icons.mjs` 生成 ICO/PNG/ICNS(策略:ImageMagick > sharp > 纯 Node fallback,幂等)。

缓存与原生依赖:Windows 侧**无 Electron 依赖**(根工程无 electron / electron-builder / electron-updater),Linux 容器也不需要 Electron 缓存卷。

## 5. 冒烟测试

- **Windows 桌面壳**(`packaging/smoke-test-tauri.ps1`,14 项):端口监听 / 同进程(无后端子进程)/ session 令牌 / SPA 首页 / 静态资源 / 桥接自检 `runtime=desktop` / 标题栏拖拽区 / 自绘三键 / 窗口层命令通道 / 单实例(二次启动不产生第二实例)/ 首实例存活 / 退出后端口释放 / launchAtLogin 落盘 + 开机自启写入注册表。
- **Windows 服务控制**(`packaging/smoke-test-service-control.ps1`,19 项):`getRuntimeControl` 字段(`managedBy=embedded` / `canPause` / `canExit` / `exitAction`)/ 暂停网关面后 3460 释放且 3462 仍在线 / `getGatewayStatus=stopped` / 恢复后 3460 重新监听 / 内嵌模式 `stopService` 被拒且壳与管理面存活 / 退出后双端口释放。
- **Windows 安装包实测**(`packaging/verify-installer.ps1`,26 项):静默安装 → 主程序/卸载器/VC 运行库/前端 SPA/能力契约在位 → 开始菜单 + 桌面快捷方式 → HKCU 卸载项 → 启动后管理面可用(令牌/getAppInfo/版本号/getConfig/SPA/能力契约)→ 数据目录 `%APPDATA%\WRouter\data` + `auth_token` 未被重建 → 进程树 RSS → 静默卸载后程序文件/快捷方式/注册表清干净且用户数据保留。
  > 期望版本号**从安装包文件名推导**(`WRouter_<ver>_x64-setup.exe`),不写死 —— 否则每次升版都会产生假 FAIL。
- **资源来源决定性验证**(`packaging/verify-resource-origin.ps1`):临时移走仓库里的 `frontend/dist`(模拟没有源码树的机器)→ 已安装的程序仍能取到 SPA 首页与**真实**能力契约(非内联 fallback)→ 证明资源确实来自安装包。
- **Linux**(`packaging/smoke-test-linux.sh`,容器内零本机影响):RPM 安装 → 文件清单核查(无 Electron/webkit/mesa/共享库)→ 单二进制静态性(ldd 报 "not a dynamic executable")→ SPA 入口/静态资源/SPA fallback(未知路径回落 index.html)/API 404 不被吞/session 令牌 → 卸载后单元与二进制随之清除 → 用户数据保留。
- **systemd**(`packaging/smoke-test-systemd.sh`):服务安装/启停/自启/杀进程自拉起/journald + 管理面 SPA 浏览器可达 + `~/.wrouter` 数据目录。

## 7. 故障排查

| 现象 | 原因 | 解决 |
|---|---|---|
| `tauri build` 卡在 NSIS 下载 | github.com 不达 | 先跑 `packaging/fetch-tauri-nsis.ps1`(镜像 + SHA1 预置到 `%LOCALAPPDATA%\tauri\NSIS`) |
| `bundleVcRuntime` schema 报错 | CLI 2.12.4 的键名是 `bundleVCRuntime`(大写 VR) | 用 `bundleVCRuntime` |
| 安装后窗口白屏 / 404 | 后端 `frontend_dir` 默认指向源码树 | 壳必须把 `WROUTER_FRONTEND_DIR` 指到随包资源(`<安装目录>\frontend`) |
| 容器内 `set: pipefail: invalid option name` | 脚本在 Windows 上被写成 CRLF,容器内 bash 不认 | 容器内执行的 `.sh` 必须是 LF 行尾(报错信息有误导性) |
| 校验脚本莫名 FAIL(与实际产物不符) | 脚本里写死了期望版本号 | 期望版本从安装包**文件名**推导,别写死 |
| PowerShell 脚本 `unexpected token` | Git Bash 下行尾被 LF 化 | `sed -i 's/$/\r/' packaging/*.ps1`;提交前 `git ls-files --eol` |
| 桌面壳测试 0xC0000135 / 0xC0000139 | 链接了 WebView2 的 harness 在 GNU 工具链下起不来 | 加 `--target x86_64-pc-windows-msvc`;纯逻辑用例已拆到 `--test pure_logic` |
| `systemctl --user enable` 报 unit not found | 单元未随包安装 | 确认 `packaging/wrouter.spec` 的 `%files` 含 `/usr/lib/systemd/user/wrouter.service` |
| 容器内 `docker: command not found` | 用 WSL 的 `bash` 跑了构建脚本 | 用 Git Bash(`scripts/build.mjs` 自动探测,可用 `WROUTER_BASH` 指定) |

清理重来:

```bash
rm -rf backend/dist backend/target      # 后端产物
rm -rf dist/win-unpacked build/dist     # 安装包产物
```

进容器调试:

```bash
docker run --rm -it -v "$(pwd):/build" -u root wrouter-linux-builder:v2 bash
```

构建速度参考:Linux 宿主 cargo-zigbuild(~12s 增量)+ vite(~10s)+ 容器 rpmbuild(~5s),合计 ~1 min;Windows NSIS 首次 ~3 min(NSIS 工具链预置 + cargo 全量编译,之后增量 ~30s)。
