# 韧性与凭据

> 蒸馏自 [reference/03 §9.2/§10](../reference/03-网关协议与路由.md)（现 reference 只留摘要）；行号已按当前树重新核验。路径相对 `backend/crates/`。本文只写「失败之后怎么办」：三层重试、退避、熔断、并发许可、固定窗口限流、凭据冷却与选号。模型名解析、选路四步、聚合展开、model 粘性、准入前置门见 [选路与候选计划.md](./选路与候选计划.md)；答案完成时释放并发许可与收尾见 [请求结束与吞吐计算.md](./请求结束与吞吐计算.md)；流内续写与断流语义见 [流式状态机.md](./流式状态机.md)。

## 1. 三层重试的合成

执行嵌套从外到内是 **计划 attempts → 候选链 → 同 provider 原地重试**（`routing/execution_plan.rs:3-5` 的模块注释同此序）；reference §10 的 ①/②/③ 是从内到外编号，不要当执行序。非流入口 `request_with_fallback`（`gateway/forward/json.rs:916`），流式入口同构循环（`forward/stream.rs:599-629`）。

```
plan.attempts[0] ─ candidate A ─ attempt 0..=max_retries（同 provider 原地重试）
                  ├ candidate B ─ ...
plan.attempts[1] ─ ...                    # 预算 16 跨以上全部层共用
```

| 层 | 谁产出 | 何时推进 | 关键实现 |
| --- | --- | --- | --- |
| attempts | `create_route_execution_plan`（`routing/execution_plan.rs:59-113`），模式语义见 [选路与候选计划.md §7](./选路与候选计划.md) | 上一 attempt 的候选链耗尽且无终态响应 | `'plan: for`（`json.rs:957`；`stream.rs:599`） |
| 候选链 | 选路/聚合产物 `(RouteCandidate, account_id)` 序列 | 当前候选原地重试耗尽或无终态 | `for (candidate, account_id)`（`json.rs:986`；`stream.rs:629`） |
| 原地重试 | `provider.max_retries`（`json.rs:1127`；`stream.rs:816`） | `should_retry` 为真 | `while attempt <= max_retries`（`json.rs:1194`；`stream.rs:830`） |

- `max_retries` 来自 provider 配置键 `max_retries`/`maxRetries`，缺省 **3**（`wr-domain/src/provider.rs:477-486`）→ 单候选最多 `1 + max_retries` 次上游调用。首次调用同样消耗 1 次预算；`attempt` 从 0 起，`should_retry` 在 `attempt >= max_retries` 时拒绝再试（`wr-domain/src/gateway.rs:33-36`）。
- **总预算**：请求级 `reliability.retryBudget`，默认 `DEFAULT_RETRY_BUDGET = 16`（`wr-infra/src/config.rs:341`），解析下限 **1**（`:422-428`，`int_key_lenient` 的 `max(lo)` 在 `:597-602`）。预算跨 attempts/候选/原地重试共用，每次真正发上游前扣 1（`json.rs:1195-1200`；`stream.rs:864-871`）；归零 `break 'plan` 并以带预算值的错误收尾（`json.rs:1532-1536`；`stream.rs:865-869`）。
- 三层相乘的例：`retry` 计划 `retryCount=2`（3 attempts）× 2 个候选 × `max_retries=3`（4 次/候选）= 理论上限 24 次，预算 16 会先截断。
- 预算只约束出站调用：规划拒绝等未触达上游的分支不扣预算（`stream.rs:831-840` 在扣减之前）。
- 预算归零不吞已捕获的兜底响应：`last_fallback_response` 优先返回（`json.rs:1537-1539`）。候选耗尽时也靠它把最后一个真实响应（如 502/429）原样给客户端，而不是网关自造错误（`json.rs:1467-1478`）。
- 非流候选推进受 `should_fallback_mode` 门控（`json.rs:1467`）；流式显式**不做**该门控，候选耗尽直接推进下一 attempt，失败状态走信封/中断（`stream.rs:573-575`，注释在代码内）。

## 2. 状态码：可重试、不可重试与回退阈值

| 集合/函数 | 取值与语义 | 位置 |
| --- | --- | --- |
| `RETRY_STATUS_CODES` | `[408,409,429,500,501,502,503,504]`（可重试码清单；`should_retry` 实际按分类判定，不直接查该表） | `wr-domain/src/gateway.rs:17` |
| `NO_RETRY_STATUS_CODES` | `[400,401,403,404,422]` | `:14` |
| `classify_route_failure` | `0→retryable`、`429→rate-limit`、`408/409→retryable`、`>=500→server`、其余 `client` | `:21-29` |
| `should_retry` | `attempt < max_retries` 且不在 NO_RETRY 且类别 ∈ `{rate-limit,retryable,server}` | `:33-44` |
| `should_fallback_mode` | `status < 400` → **false**；`model-chain` 对任意 `>=400` → true；其余模式仅三类可回退 | `:49-60` |

逐状态的行为矩阵（非流口径；流式差异见下）：

| 上游结果 | 原地重试 | 非流候选推进 | 终态/兜底 |
| --- | --- | --- | --- |
| `0` 网络失败 | 可（类别 retryable） | 循环自然推进 | 无响应可兜底 |
| 400 普通 | 否（NO_RETRY） | 否 | 原样透传 400 |
| 400 上下文超限 | 否 | 可（S7） | 保留响应兜底 |
| 401/403 | 否（NO_RETRY，凭据类） | 可 | 全候选耗尽回真实响应 |
| 404/422 | 否（NO_RETRY） | 否 | 原样透传 |
| 408/409 | 可 | 若仍失败且 `should_fallback_mode` 为真 | 兜底最后响应 |
| 429 且 `Retry-After ≤ 60s`/无 | 可（等 Retry-After 或退避） | 重试耗尽后可 | 兜底最后响应 |
| 429 且 `Retry-After > 60s` | 否（跳过原地） | 可 | 兜底最后响应 |
| 500/501/502/503/504 | 可（`server`） | 可（`off/retry` 也回退） | 兜底最后响应 |
| 501 | 可 | 可 | 但熔断视为成功（§4） |

- 网络层失败用哨兵 `status = 0`：可原地重试；`should_fallback_mode(0)` 为 false，候选推进由循环自然完成（`failure_classifier.rs:73-81` 的断言解释了这一点）。
- **401/403 是凭据类失败**：不原地重试，非流推进下一候选并把真实响应留作兜底（`json.rs:1373-1400`，常量 `CREDENTIAL_FAILURE_STATUS_CODES` 在 `gateway.rs:122`）；流式暂存真实握手错误，全候选耗尽后回真实状态而非吞成 502（`stream.rs:1156-1172`、`:583-590`）。
- **404/422 保持终态**：非流直接 `terminal` 透传（`json.rs:1401-1409`），流式以错误信封结束（`stream.rs:1148-1207`）。普通 400 同属终态；但 400 正文命中上下文超限方言时走「不重试同模型、推进下一候选」（`json.rs:1344-1372`；`stream.rs:1128-1147`）。
- **501 的分裂**：在 `RETRY_STATUS_CODES` 内且类别为 `server`（可重试/可回退），但默认熔断计票集不含 501；`record_response(501)` 反而按成功清零计数（`breaker.rs:137-145`，单测 `:399-413`），断言固化在 `failure_classifier.rs:61-71`。
- 409 属 retryable（`gateway.rs:25`），可原地重试——与 404/422 的终态口径不同。

## 3. 退避与等待

```
backoff(n) = min(1s × 2^n, 30s)                     # gateway.rs:63-65
retry_wait = Retry-After>0 ? clamp(ms, 1, 60000)/1000
                          : backoff(attempt) × (0.5 + U[0,1))   # :96-107
```

- 抖动区间是 `[0.5, 1.5)`（上界不含）；退避分支最长 `30 × 1.5 = 45s`，**[1,60000]ms 夹紧只作用于 Retry-After 分支**（`:101-106`）。
- Retry-After 解析支持正数秒（可带小数）与 RFC2822 HTTP-date，负数/垃圾串 = 无（`gateway.rs:68-84`）。
- `retry_after_exceeds_cap` 判 `> 60_000ms`（`gateway.rs:114-116`），**仅 429 消费**：不再原地等，直接推进下一候选（`json.rs:1411-1418`；`stream.rs:1208-1215`）；503 等仍保留原退避语义（`:109-113` 的注释）。
- 等待来源落 `wait_source = "retry-after" | "backoff"`（`:104-106`），尝试行的 `wait_ms` 与实际睡眠同源（`forward/support.rs:38-50`）；`retry_wait_now` 用 `WeightedRng`（splitmix64，`credential_pool.rs:510-531`）取随机数。
- **先算后睡，且退避前让出许可**：非流在睡眠前 `drop(permit)`、醒后重取（`json.rs:1238-1262`、`:1439-1463`）；流式同样 `drop(permit.take())`，睡眠用 `sleep_wait_or_abort` 感知客户端断开（`stream.rs:1236-1262`；`support.rs:70-78`）。
- 重取许可被拒是**请求级终态** 429（`ForwardFailure::QueueRejected`），不推进候选（`json.rs:1242-1262`；`stream.rs:1263-1298`）。

## 4. 熔断

纯状态机在 `wr-domain/src/gateway.rs:405-488`；应用层与持久化在 `gateway/breaker.rs`。

- 状态 `Closed / Open / HalfOpen`（`gateway.rs:405-422`）；状态体 `{consecutive_failures, opened_until_ms, last_state_change_ms}`（`:425-430`）。
- `compute_status`（`:445-458`）：`opened_until_ms <= 0 || failures < threshold` → `Closed`；`now < opened_until_ms` → `Open`；否则 `HalfOpen`。读取侧不使用 `cooldown_ms` 形参（`_cooldown_ms`），冷却只在写开闸时刻时消费。
- `record_failure`（`:465-479`）：先算当前态，再 `failures += 1`；若当前是 `HalfOpen` **或** 累计达到阈值 → `opened_until_ms = now + max(1, cooldown_ms)`、立即返回 `Open`，否则返回原态。计数只在成功时清零，不在开闸时清零。
- `record_success`（`:482-488`）：`failures = 0`、`opened_until_ms = 0`；`last_state_change_ms` 仅在为 0 时写入（保留首次变更时刻）。
- 事件视角：

| 当前态 | 事件 | 结果 |
| --- | --- | --- |
| `Closed` | 失败但未达阈值 | 保持 `Closed`，计数累加 |
| `Closed` | 失败后累计达阈值 | `Open`，`opened_until = now + cooldown` |
| `Open` | 请求到达且 `now < opened_until` | `is_open` 为真，候选被跳过 |
| `Open` | 冷却到期（未发生新失败） | 推导为 `HalfOpen`，请求放行试探 |
| `HalfOpen` | 试探失败 | 立即重开，冷却从当前时刻重新计 |
| `HalfOpen` | 试探成功 | `Closed`，计数与开闸时刻清零 |

- `HalfOpen` 是**推导态**，不持久化，也**没有单试探锁**：冷却到期后所有看到该状态的并发请求都可放行试探。
- 应用层：`is_open`（`breaker.rs:110-124`，`enabled=false` 恒 false）；`record_response` 只把命中 `failure_status_codes` 的状态记为失败，其余一律 `record_success`（`:127-146`）；`record_failure/record_success` 包一层持久化（`:149-193`）。
- **计票集**为全局 `CircuitBreakerConfig.failure_status_codes`，默认 `[408,429,500,502,503,504]`（`wr-infra/src/config.rs:52-60`、`:85-90`）；provider 级只覆盖 `failure_threshold`/`cooldown_ms`（>0 才覆盖，`breaker.rs:246-258`），**不能**改计票码。
- **只在状态跃迁时落库**：失败后 `after==Open` 或失败前是 `HalfOpen` 才写（`breaker.rs:160-169`）；成功只在失败前不是 `Closed` 时写（`:183-192`）。写失败只告警，内存仍是权威（`:237-241`）。启动 `reload`（`:82-104`）把超出一年 horizon 的 `opened_until_ms` 归一为已到期，防止异时钟基把 provider 永久锁死（`:90-100`）。
- 熔断只做**候选过滤**：非流候选循环里 `is_open` 为真就静默 `continue`（`json.rs:1006-1011`）；流式则先落一条 `0/"circuit breaker open"` 尝试行再跳过（`stream.rs:711-722`）。聚合健康门（`model_groups.rs:128`）、钉扎/组粘性健康门（`routing.rs:94`、`:330`）同样读 `is_open`。没有「熔断打开时返回 503」的生产分支——`breaker_failure_response`（`breaker.rs:262-272`）当前未被调用。
- 记分点：非流 `<400` 记成功、`>=400` 走 `record_response`（`json.rs:1322-1343`），网络错误记失败（`:1223-1225`）；流式握手状态 `record_response`（`stream.rs:1120-1127`）、成功后 `record_success`（`:1528`）、答案结束前的流内传输错误记失败（`:1885-1891`），答案结束后的尾部断流不驱动熔断（`:1876-1884`）。

## 5. 并发许可与固定窗口限流

两者都产 429，但管的事不重叠：**信号量管同时在飞**，**固定窗口管时间窗内的量**；键空间、存储与判定时机都不同。

| | `gateway/concurrency.rs` | `gateway/limits.rs` |
| --- | --- | --- |
| 管什么 | 每 provider 同时在飞的请求数 | 每身份、每作用域、每指标的窗口计数与预算 |
| 结构 | 每 provider 一个 `tokio::sync::Semaphore`，按 provider id 缓存（`:36-40`、`:52-62`） | `Prechecker` + 内存固定窗口（`:114-118`、`:90-111`） |
| 容量 | provider `max_in_flight`（>0）覆盖全局 `max_in_flight_per_provider`，默认 **8**（`config.rs:103-110`；`concurrency.rs:53-56`） | 指标 `rpm/rph/rpd/tpm/tph/tpd/ipm`（`:30`），默认窗口 60s/3600s/86400s（`:33-41`） |
| 拒绝 | 槽满/排队超时 429；客户端断开 499 | 限流 429、预算 402（`:276-293`、`:207-222`） |
| 时机 | 选定候选、发上游之前（`json.rs:1018`；`stream.rs:725`） | 进路由之前（`json.rs:232-276`；流式同序） |

- `queue_timeout_ms` 默认 **0**（`config.rs:108`，下限 0 在 `:128-134`）：`<=0` 走 `try_acquire`，槽满立即 429（`concurrency.rs:84-96`）；`>0` 走 `timeout(wait, acquire_owned)`，超时或信号量关闭均 429（`:97-115`）。
- `enabled=false` 每次发一个 1_000_000 容量的空许可（`:66-74`，该分支先返回、不看 aborted）；`aborted()` 为真在拿槽前返回 499/aborted（`:75-82`）。非流传 `|| false`，流式传客户端断开闭包。
- 配置按「acquire 前快照同步」生效（`sync_config`，`concurrency.rs:44-46`；调用点 `json.rs:82-83`）。但信号量容量在**首次为该 provider 建池时固定**（`or_insert_with`，`:52-62`），运行期改 `max_in_flight` 只影响尚未建池的 provider。
- 非流拿不到槽直接 `QueueRejected` 并终止请求（`json.rs:1021-1057`，注释 `:1012-1015` 说明这是 20261016_01 A-3 的收紧），不静默超发也不推进候选。
- 许可生命周期：候选开始拿槽 → 跨上游调用持有 → 退避前 `drop`、睡醒重取（`json.rs:1240/1441`）→ 候选结束统一 `drop(permit)`（`json.rs:1484`；`stream.rs:2664`）。流式用 `Option` 持有许可，答案完成即提前释放（`stream.rs:738-741`），细节在 [请求结束与吞吐计算.md §2](./请求结束与吞吐计算.md)。
- 固定窗口是**非滑动**：`window_start = now - now.rem_euclid(window_ms)`（`limits.rs:265`），键 `{identity}:{scope}:{metric}:{window_start}`（`:270`），窗口换了就是新键；因此老桶不回收（模块注释 `:6-11`）。计数先加后比 `used > limit`（`:271-293`），被拒请求**已吃进窗口的量不回滚**；预算则先加、超限后 `add_cost(-cost)` 冲销并 402（`:189-225`）。
- 作用域：`global` 规则受 `precheck.enabled` 门控（`:172-182`），API key 的 `key` 规则**不受门控**（`:183-188`）；身份键取 `x-api-key`/`api-key`/`Authorization: Bearer` 前 12 字符，否则 `anonymous`（`:351-371`）。
- 凭据池里另有一套按账号的固定窗口计数（键 `{provider}::{account}::{rule}::{window_start_ms}`，`credential_pool.rs:108-116`、`:463-503`），当前**无生产调用点**（模块注释 `:31-32`），不要把它与 precheck 的 `{identity}:...` 键混为一谈。

## 6. 凭据池：失败分类与冷却

凭据池是进程内运行态（重启清冷却），权威池行在 sqlite `provider_accounts`（`credential_pool.rs:4-10`）。生产写入走 `record_outcome_classified`（`:312-359`）：先按 `classify_rest_class`（`wr-domain/src/rest.rs:138-189`）判语义类别，再用 `rest_duration_ms`（`rest.rs:256-269`）算时长，作用域由 `RestClass::is_account_scoped`（`rest.rs:65-70`）决定。分类输入是 `status + body + error_type + code`（`rest.rs:138-144`），无线索时按状态码兜底（429→`RateLimit`、401/403→`Auth`、`>=500`→`ServerError`，`:148-183`）；口径刻意保守——误分类会把活账号锁几小时，代价高于少判一类（模块注释 `:17-19`）。

| 类别 | 触发（摘要） | 冷却时长 | 作用域 |
| --- | --- | --- | --- |
| `Quota` | 429 且正文/码命中 quota | 厂商 reset（上限 `QUOTA_RESET_MAX_MS = 8d`，`rest.rs:221`）；无 reset → 梯子 | 账号 |
| `Credit` | 402；或 401/403/429 正文命中余额/欠费 | `rest_base_ms = 30m`（`rest.rs:210`） | 账号 |
| `Restricted` | 401/403/429 正文命中 suspend/restricted | `2h`（`:211`） | 账号 |
| `Verify` | 401/403/429 正文命中验证/captcha | `30m`（`:212`） | 账号 |
| `Auth` | 401/403 默认 | `300s`（`:213`，与 `CREDENTIAL_COOLDOWN_MS = 300_000` 同值，`credential_pool.rs:52`） | 账号 |
| `RateLimit` | 429 默认 | reset（≤24h，`rest.rs:262-265`）；无 reset → `DEFAULT_COOLDOWN_MS = 60_000`（`credential_pool.rs:45`、`:333-336`） | 模型 |
| `ServerError` | `>=500` | `60s`；**忽略 reset**（`rest.rs:267` 的兜底臂） | 模型 |
| `Unknown` | 无状态码传输失败 | 指数梯子（见下） | 模型 |

- **梯子确实存在，但不是 1m→10m 两档**：`rest_ladder_ms` 首次 60s，之后每次翻倍 `60s→120s→240s→480s→600s` 封顶 10 分钟（`rest.rs:195-201`，单测 `:348-356`）。它只服务 `Unknown`（及无 reset 的 `Quota`）；`record_outcome_classified` 只在 `should_cooldown`（401/403/429/`>=500`，`credential_pool.rs:119-121`）时写冷却，所以 400/404 即便分类为 `Unknown` 也不进梯子。
- 无 HTTP 状态码的传输失败（流内中断、连接错误）走 `record_transport_failure`：直接 `rest_ladder_ms`、模型级、不封整把 key（`:366-385`）。
- Retry-After 只对 **429/5xx** 采集（`forward/cache_io.rs:209-224`：头优先，429 无头时解析错误正文的 reset 文本），但 `rest_duration_ms` 只让 `Quota`（≤8 天）与 `RateLimit`（≤24h）消费 reset；`Auth/Credit/Restricted/Verify/ServerError` 忽略 reset。`MAX_RETRY_AFTER_COOLDOWN_MS = 86_400_000`（`:55`）仅被单测引用，真正的 24h 上限是 `rest.rs:264` 的内联字面量。
- 历史分档函数 `cooldown_tier`（401/403→300s、429/`>=500`→60s，`credential_pool.rs:126-133`）仍在，但**只被单测引用**；生产时长为上表的语义路径。不要按它推断 5xx 会遵守 Retry-After。
- 冷却到期加**确定性抖动**：种子为 `{provider}::{account}` 或加 `::{model}`（`:396-402`），幅度 `span = min(duration/5, MAX_COOLDOWN_JITTER_MS=30_000).max(1)`，FNV-1a + splitmix 终混后取 `[0, span]`（`:81-96`）；到期 = `now + duration + jitter`（`:337-340`）。同键恒同偏移，不同键摊开集体恢复时刻。
- 作用域落键 `store_cooldown`（`:406-424`）：账号级类别写 `{provider}::{account}`；模型级写 `{provider}::{account}::{model}`；无模型维度时退回账号键（更严）。`is_cooled_down_for_model` 先查账号再查模型（`:205-227`），账号冷却屏蔽该账号全部模型。
- 连续失败计数按**账号键**累计，即使冷却写在模型键上（`:330`、`:388-393`）——同账号不同模型共用同一梯子高度。
- 任何 `2xx–4xx` 且不属于 `{401,403,429}` 的状态都视为「用过」，同时清账号键、模型键与失败计数（`:349-358`，谓词 `:136-138`）；`clear_cooldown` 也清两域并复位梯子（`:446-459`），供管理面 RPC 使用。

## 7. 凭据池：选号

`pick_account_with_model`（`credential_pool.rs:566-617`）先取 `enabled` 账号（保持配置顺序，`:573-583`），再按 provider 的 `credential_strategy` 选：

| 策略 | 行为 | 位置 |
| --- | --- | --- |
| `first` | 可用集中取 `priority` 最大，同优先级先见者胜 | `:640-648` |
| `pinned` | 严格固定 `pinned_account_id`；enabled 才返回，**无视冷却也不回落** | `:584-589` |
| `weighted` | `weight.max(1)` 累计减权随机抽取 | `:652-670` |
| `balanced` | 可用集最高 priority 层内再做 weighted（主备 + 层内均衡） | `:622-637` |
| `sticky` | 有会话键走加权 rendezvous：`score = u^(1/w)`，`u = SHA-256(session_key∥account_id)` 归一（`wr-domain/src/gateway.rs:184-192`），取最大；无会话键降级 weighted | `:675-687`、`:611-614` |

- 「可用」= 账号级与模型级都未冷却（`:590-594`）。**全部冷却时**不再盲打第一个，而是探**最早恢复**的账号（按 `cooldown_remaining_ms_for_model` 取最小，`:595-606`，取账号级与模型级的较大剩余 `:230-247`）；这是有意的 fail-open 试探。
- 可用集为空时，除 `pinned` 外的所有策略都由上面的探最早分支返回一个账号；候选为空（或 `pinned` 账号不可用）才返回 `None`，调用方保留 legacy 单密钥（`forward/credential.rs:23-35`）。
- 随机源是 `WeightedRng`（splitmix64，`wall_ms` 旋转 + 进程内计数器做种，`:510-531`），同毫秒并发也不会拿到相同序列；单测注入固定闭包（`:552-559`）。例：A/B 同优先级、权重 3/1，`weighted` 抽中 A 的概率为 3/4；`balanced` 先取可用集最高优先级层，层内再按同一权重抽（`:622-637`）。
- 注入：默认入口按策略选号后调用指定账号版（`forward/credential.rs:17-40`），后者只在该账号 enabled、`account_secret` 非空时替换 `provider.api_key`；空密钥不覆盖 legacy，账号 id 仅在实际注入时返回 `Some`（`:46-75`、`credential_pool.rs:694-703`）——`x-wr-account` 与凭据结果记录都以它为准。
- 选号时传入的 `model` 是本次候选的实际模型名（`json.rs:1307`；`stream.rs:1115`），所以模型级冷却只剔除该模型；请求级会话键提取与 model 粘性属 [选路与候选计划.md §6](./选路与候选计划.md)，选号只消费它。
