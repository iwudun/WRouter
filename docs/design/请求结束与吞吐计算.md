# 请求结束判定与解码/输出速度

> 当前机制蒸馏自 planning [20261108_01](../planning/20261108_01_请求结束判定与吞吐计算统一优化方案.md) §4/§7/§13；唯一实现 `backend/crates/wr-infra/src/sqlite/usage_store.rs`。日志键契约见 [reference/03 §13.1](../reference/03-网关协议与路由.md) 与 `frontend/src/contracts/logs.ts`。

## 1. 为什么有两个速度

单看「output ÷ 总耗时」会把首字等待、隐藏思考、排队代理都算进解码速度，掩盖真实生成快慢；单看「可见内容 ÷ 内容流窗口」又会在隐藏思考上游（Responses 加密 reasoning）把分子多算一段没有对应时间的 token，虚高到数百上千。因此拆成两个互补指标：

| 指标 | 分子 | 分母 | 守卫 | 衡量 |
| --- | --- | --- | --- | --- |
| `decodeTps`（解码速度） | 可见输出 token | 实测内容流窗口 | 有（短样本/突发） | 内容实际生成速度 |
| `outputTps`（输出速度） | 全部上报 `output_tokens` | 请求总耗时 `duration_ms` | 无内容流守卫 | 含首字/思考/排队/代理的整体速率 |

失败/取消行与在途行两者均为 null。前端不再二次计算，直接展示后端值（后端单一事实源）。

## 2. 请求结束判定（Finish 锚点）

时间轴：

```
t_start ─ TTFT ─ [思考段] ─ t_answer_first ─ [答案段] ─ t_answer_end ─ [拖尾] ─ t_stream_end
```

- **完成锚点前移到 `t_answer_end`**：共享观察路径（`RecordEncoder` → `SourceObserver`，Raw 与转换都经过）观察到语义 `Finish` 事实时记录。各协议来源：OpenAI `finish_reason`、Anthropic `message_delta.stop_reason`、Responses `response.completed`、Gemini `finishReason`。
- **冻结主耗时**：成功流式行 `duration_ms = t_answer_end − t_start`（不再用排空终点）；无 `Finish` 事实（纯工具调用/异常中断）回退 `t_stream_end`。
- **提前释放并发许可**：`drop(permit)` 在 `t_answer_end`，拖尾不占槽。
- **停在途计时**：在途条目记 `answer_end_ms`，前端插值 `min(now, answerEnd) − createdAt`，答案完成即停跳。
- **有界收尾 grace**（默认 5s，`streamTerminalGraceMs`）：`t_answer_end` 后继续排空捕获尾随 usage / `[DONE]` / 缓存聚合，到期以 `completed` 写日志（缺 `[DONE]` 只是簿记缺失，非失败）。
- **空闲超时**（默认 90s，`streamIdleTimeoutMs`，SSE ping 不续命）：无 Finish 也无 EOF 的挂连接到期以 `502 stream_incomplete` 收尾。
- 日志写点 = `min(t_stream_end, t_answer_end + grace)`；`duration_ms` 始终冻结在 `t_answer_end`。`stream_tail_ms` 仅诊断，不计入耗时。

## 3. 计时窗口（FlowMeter）

`flow_ms` / `answer_flow_ms` 是内容 **10%→90% 推进跨度 ×10/8** 折算，**不是墙钟耗时**（用 flow 而非 `last − first` 是为对边缘网络抖动鲁棒）。

| 键 | 含义 |
| --- | --- |
| `first_byte_ms` | 全内容首字（含思考首字） |
| `flow_ms` | 全内容 10%→90% 窗口（含可见思考/工具参数） |
| `first_answer_byte_ms` | 答案首字（答案窗口起点） |
| `answer_flow_ms` | 答案内容 10%→90% 窗口（排除 ReasoningDelta） |
| `reasoning_decode_ms` | 思考段跨度（诊断 + 隐藏思考分支判据） |
| `reasoning_content_bytes` | 思考可见文本字节（隐藏思考分支判据） |
| `answer_end_ms` | 答案完成耗时（新行断代标记） |

答案内容字节 = `PartDelta` 文本 / `RefusalDelta` / `ToolArgumentsDelta` / 非空文本块起始，**排除 `ReasoningDelta`**。插桩统一在 `pump.mark_flow(&facts)`（Raw 与转换共用），终态后 `observation_only` 提前返回不再打点 → 天然止于答案结束。

## 4. decodeTps 条件公式

唯一实现 `decode_tps_sample`（`usage_store.rs:757`）。**分子分母必须覆盖同一集合**。

### 4.1 默认（全内容，FullFlow）

```
decodeTps = output_tokens / (flow_ms / 1000)
```

分子含思考与工具参数，分母 `flow_ms` 同样含可见思考/工具参数。适用：Ling（只发 `reasoning_content` 不报 `reasoning_tokens`）、思考可见的 Chat、Gemini/Anthropic、缺 `provider_protocol` 的旧行。

### 4.2 隐藏思考（答案流，AnswerFlow）

```
decodeTps = max(output_tokens − reasoning_tokens, 0) / (answer_flow_ms / 1000)
```

窗口起点用 `first_answer_byte_ms`。触发条件 `strips_hidden_reasoning`（`usage_store.rs:704`）：`reasoning_tokens > 0` 且——

- `provider_protocol == "openai_responses"` → 无条件剥离（reasoning 默认加密块，只有计数没有可测流）；
- `provider_protocol == "openai"` → `reasoning_decode_ms` 缺失/≤0 时剥离；有思考计时但 `reasoning_content_bytes < reasoning_tokens`（摘要/单块折叠）也剥离；
- 其余（Gemini output 本就不含 thoughts、Anthropic、缺字段旧行）→ 不剥离。

典型：AgentRouter 1622 全输出含 1216 隐藏思考 → 按 `406 / answer_flow` 算（≈75 tok/s），而非 `1622 / flow`（≈301）。`provider_protocol` 在请求落库时写入（见 [协议交换.md §2](./协议交换.md)）。

### 4.3 短样本守卫（新行，有 answer_end_ms）

按分支取窗口（默认 `flow_ms` / 隐藏 `answer_flow_ms`），任一命中 → 无样本（`usage_store.rs:805-818`）：

| 守卫 | 条件 | 常量 |
| --- | --- | --- |
| 分母不可测 | flow ≤ 0 / 单点 / 零跨度 | — |
| 窗口下限 | flow < 100ms | `MIN_DECODE_MS = 100` |
| 短样本长等待 | flow < 1000ms 且 window_start > 4×flow | `HELD_WINDOW_MS = 1000`、`HELD_SHARE = 4` |
| 批量投递 | flow×4 < gen_window（gen_window = answer_end − window_start） | `HELD_SHARE = 4` |
| 物理上限 | 分子/(flow/1000) > 1000 tok/s | `BURST_MIN_TOKENS_PER_SECOND = 1000` |

常量定义 `usage_store.rs:1062-1083`。「短样本长等待」与「批量投递」对齐 magpie `MinDecodeMs` / `HeldWindowMs`，剔除长思考后整段倒出的短答案/短工具参数。

### 4.4 旧行（无 answer_end_ms）

沿用解码窗口 `duration_ms − first_byte_ms` + 既有突发守卫，来源标记 `LegacyDecodeWindow`。旧数据不迁移；新行分母不可测时**不回落**旧口径（否则同一请求在列表与统计里拿到不同分母）。

## 5. outputTps

`output_tps_sample`（`usage_store.rs:854`）：`output_tokens / (duration_ms / 1000)`。不套内容流守卫——衡量含首字/思考等待/排队/代理的整体速率。只要求成功行、`output > 0`、`duration > 0`。

## 6. 聚合与派生表

- 后端单一事实源：落库行与在途快照外，按上述公式算每行速度随 `getCallLogs` 返回；统计聚合同口径（`usage_sums_from_item`，`usage_store.rs:872`）。由此列表逐行 == 统计聚合，消除前端 TS 与后端 Rust 两套公式漂移。
- 统计页均值/P50/P95 只聚合 `full_flow` + `answer_flow` 同源样本，`legacy_decode_window` 排除。TTFT 仍用 `first_byte_ms`（含思考首字，口径不变）。
- `usage_rollup` / `usage_rollup_hist` 是派生表（`decode_tokens` / `decode_ms_sum` / `decode_source` 维度）；升级检测旧列并从 `request_logs` 重放重建，失败回滚退回原始行聚合（`schema.rs:295+`）。原始 `request_logs` 不迁移。
