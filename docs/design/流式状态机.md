# 流式数据面状态机与对账

> 蒸馏自 [reference/03 §3.3 / §7](../reference/03-网关协议与路由.md)（权威 file:line 在该处）与当前 `wr-domain/src/semantic/` 代码；冻结的事件词表、Responses 上游映射表以 reference/03 §3.3、§7.4 为准，本文不复制。本文只讲「一个上游帧如何变成语义事实、四类客户端状态机如何收口、工具参数如何对账、聚合与合成如何复用同一编码器」。协议矩阵/保真等级见 [协议交换.md](./协议交换.md)；Finish 锚点与吞吐窗口见 [请求结束与吞吐计算.md](./请求结束与吞吐计算.md)。

## 1. 管线：一帧只解码一次，多消费者共用同一份事实

```
RawRecord
└─ RecordEncoder::encode                     forward/record_encoder.rs:31
   ├─ SourceFacts::from_record               record_encoder.rs:36   ← 唯一解码点
   ├─ SourceObserver::observe                record_encoder.rs:61   ← 生命周期/用量/续写
   ├─ StreamAggregator::push / merge_snapshot record_encoder.rs:62-69（仅缓存装配）
   └─ 输出二选一
      ├─ native_raw / Passthrough：原记录字节  record_encoder.rs:80-127
      └─ ClientStream::consume_facts         record_encoder.rs:129
          └─ Delivery::emit（首批提交 HTTP 头）delivery.rs:163-203
```

- **一次解码**：`SourceFacts::from_record` 内部只调一次 `decode_upstream_frame`（`source.rs:180-221` → `stream/decode/mod.rs:44`），产出的 `events`（扁平）与 `updates`（层级）来自同一次协议解释（`decode/mod.rs:44-98`、`source.rs:151-166`）。下游观察者与编码器都读这份结果，不再各自解析 payload。
- **三类账**：Received（观察者按帧/字节计，`source.rs:383-392`）、Accepted（过生命周期门，`source.rs:397-416`）、Committed（投递层确认入队，`delivery.rs:185-201`）。`observe` 对同序号同内容的确切重放返回 `false`（`source.rs:382-395`、`:467-494`）：该帧仍计 Received，且原生 Raw 仍输出原字节，但不再喂给转换泵或聚合器（`record_encoder.rs:58-75`）。
- **终态后只观察**：`observation_only` 在 `observer.terminal()` 后为真（`stream.rs:1769`、`:2109`），编码器返回 `None`，尾随 usage/哨兵不进客户端通道（`record_encoder.rs:70-72`）。
- **写出口唯一**：所有帧（含合成帧、缓存重放、终态帧）都经 `Delivery::emit`（`stream.rs:1800`、`delivery.rs:163`）；首帧入队前提交握手，提交前失败返回真实 HTTP 状态，提交后只能用协议内错误/中断（`delivery.rs:144-160`、`:206-225`）。背压为 `mpsc::channel(8)`（`stream.rs:48`）。

**编码结果的两个事实分开**：`EncodedBatch{frames, has_content}`（`client_stream/mod.rs:208-212`）只声明「这批帧是否含模型内容」，不声明是否已交付；`Delivery` 在真正入队后置 `content_committed`（`delivery.rs:196-198`），首字打点、并发释放都读投递层事实而非编码器自报（`stream.rs:1795-1805`）。`has_content` 的判据 `is_content_event` 排除信封帧（角色占位、空文本块、空增量），只看非空 `PartDelta`/`RefusalDelta`/`ReasoningDelta`/`ToolArgumentsDelta`、`ReasoningStart`、`ToolCallStart` 与非空文本 `PartStart`（`client_stream/mod.rs:545-559`）。原生 Raw 路径用同口径的 `facts_have_content`（`:541-543`）。

**顺序不变式**：观察者先于编码器（`record_encoder.rs:61` 在 `:129` 之前），所以被生命周期门拒绝的事件不会进客户端通道；重建路径上，非 Accepted 的帧在非 Raw/非 Passthrough 时直接丢弃（`record_encoder.rs:73-75`）。这条顺序同时保证了「违规计数」与「已提交正文投影」不会错位。

## 2. 两套词汇的消费边界

| 词汇 | 生产者 | 消费者 | 能否跨帧去重 |
| --- | --- | --- | --- |
| `SemanticEvent`（扁平） | 同一次解码 | `SourceObserver`、Chat/Anthropic/Gemini 编码器、`StreamAggregator` | 编码器内可（自带状态） |
| `StreamUpdate`（层级） | 同一次解码 | 仅 `ResponsesTargetClient`（`client_stream/mod.rs:312`） | 客户端状态机内可 |

`StreamKey{candidate,item,part}` 是三级身份、`BTreeMap` 有序（`ir.rs:24-29`）；`ItemKind` 只区分 `Message/Reasoning/ToolCall/Unknown(String)`（`ir.rs:47-53`），未知协议 type 原样落进 `Unknown` 不失真。注意 `ClientStream::consume_facts` 对 Responses 分支**跳过** `repair_tool_arguments`（`client_stream/mod.rs:303-307`）——Responses 的参数补齐走 `StreamUpdate::ItemSnapshot` 对账（见 §5）。

`ResponsesTargetClient::consume` 对变体的处置分三类（`responses_target.rs:1188-1305`）：

| 类别 | 变体 | 处置 |
| --- | --- | --- |
| 建槽/写帧 | `ResponseStart`、`ItemStart`、`PartStart/Delta`、`RefusalDelta`、`Reasoning*`、`ToolStart`、`ToolArgumentsDelta`、`PartEnd`、`ItemSnapshot`、`ItemEnd` | 驱动 §4 的槽位状态机并产出客户端帧 |
| 只记事实 | `Usage`（`merge_max`）、`Finish`（覆盖为最新原因）、`ResponseSnapshot`（仅 `OpenAiResponses` 收下） | 供 finalize 组装终帧 |
| 显式空操作 | `ReasoningSignature`（不伪造签名）、`ToolResult`、`Error`、`End` | 不产帧；错误/终态由投递层与 finalize 表达 |

`consume` 末尾按 `started` 补一次 `response.created`+`response.in_progress`（`:1301-1304`、`:142-160`）：`start_emitted` 保证信封**只发一次**（且 item 收口、快照补发、finalize 也会触发它），但它不承诺「信封排在首个 delta 之前」——同一批里信封可能追加在末位。

## 3. 四类客户端状态机的收口契约

`finalize` 汇总在 `ClientStream::finalize_with_usage`（`client_stream/mod.rs:444-454`），`finalize_incomplete` **只分发 Responses**、其余协议返回空（`client_stream/mod.rs:459-465`）。

| 实现 | `finalize` 行为 | `finalize_incomplete` |
| --- | --- | --- |
| `ChatClient`（`chat.rs:230-260`） | 对**尚无**结束原因的候选补一个 `finish_reason:"stop"` 块并记入 `finishes`；已给过则不发第二个。usage 未下发时补 `choices:[]` + usage 的尾块（**不带** finish_reason，`chat.rs:262-279`）；最后 `[DONE]` | 空（不适用） |
| `AnthropicClient`（`anthropic.rs:387-412`） | `flush_start` → 关闭所有未闭合块 → 一条 `message_delta`（`stop_reason` 取语义 Finish；缺失时回退 `tool_use`/`end_turn`，`anthropic.rs:397-401`）→ `message_stop`。整条流只输出一次终结序列 | 空 |
| `ResponsesTargetClient`（`responses_target.rs:1307-1395`） | 关闭打开中的 item（`close_open_items`）→ 补齐快照里未输出过的 item → `response.completed` 或 `response.incomplete`（`finish == IncompleteOther` 时，`:1338-1339`）→ `[DONE]` | 同一条收口路径但 `force_incomplete=true`：先收口 item（断流前内容必须进 output），终帧 `response.incomplete` + `incomplete_details.reason="upstream_stream_incomplete"`，**不合成成功** |
| `GeminiClient`（`gemini.rs:261-268`） | **不产出终结序列**：只 flush 尚未输出的工具调用（参数完整才发 `functionCall`，`gemini.rs:43-77`）。`finishReason` 只由上游 `Finish` 帧触发（`gemini.rs:229-242`），缺失则流由 EOF 截断 | 空 |
| `Passthrough` | 空（`client_stream/mod.rs:451`），原字节由管线直出 | 空 |

共同约束：**一条流只能有一个终止字段，且沿用上游真实取值**；兜底默认值只在上游完全没给时补（Chat 的 `stop`、Anthropic 的 `tool_use`/`end_turn`），否则严格客户端会判 `conflicting_finish_reason`。

收口帧序（正常 EOF）：

```
Chat       [上游已给 finish] … (choices:[] + usage) [DONE]
           [上游未给 finish] … (finish_reason:"stop" [+usage]) (+usage 尾块) [DONE]
Anthropic  message_start … content_block_stop×N message_delta message_stop
Responses  output_text.done/content_part.done … output_item.done …
           response.completed (output/output_text/usage 明细) [DONE]
Gemini     (flush 未输出的 functionCall)  ← 无终结帧，靠上游 finishReason 帧
```

Responses 的 `[DONE]` 是裸哨兵（`responses_target.rs:1393`），与上游 `[DONE]` 解码成 `StreamEnd{incomplete:false}`（`decode/mod.rs:45-52`）是同一语义在两侧的落点。原生 Raw 路径**不调用**这些收口（`stream.rs:2255-2258`、`:2318-2321`），也不合成成功终态。

## 4. Responses 分槽、`next_output_index` 与 opaque 判定

客户端状态（`responses_target.rs:20-39`）：`output: BTreeMap<usize, Value>`（已完成 item，最终 output 顺序）、`items: BTreeMap<usize, ResponsesItem>`（打开中的 item/part 槽）、`item_for_key: HashMap<StreamKey, usize>`（上游 item 键 → 客户端 index）、`next_output_index`、`finish`、`snapshot`、`conflicts`。

- **单调分配**：`allocate_item` 先按 `StreamKey::item(candidate,item)` 复用已有 index；不命中才取 `next_output_index` 并自增（`responses_target.rs:162-190`）。快照补发同样自分配（`:1033-1034`）。客户端 index 与上游 `output_index` **解耦**，映射只经 `item_for_key`；同一 item 的未知 kind 在后续 `ItemStart` 时原地升级（`:172-176`）。
- **opaque 判定树**（`:1289-1298`）：`StreamUpdate::Opaque` 只在 `raw.type` 以 `"response."` 开头时原样转发，异协议 opaque 不冒充 Responses 事件。解码层的 opaque 只来自「协议未识别且无事件」的兜底（`decode/mod.rs:88-91`）；`response.output_item.done` **不**走 opaque，而是 `ItemSnapshot` + `ItemEnd`（`decode/responses.rs:113-133`）。
- **item 收口**：`ItemEnd` → `item_end` 关 part、生成 `function_call_arguments.done`/`output_item.done` 并写入 `output`，随后 `forget_item` 清掉键映射（`responses_target.rs:819-956`）。工具缺名或参数不是完整 JSON 时**发协议内 error 帧**，不伪造 `{}`（`:835-867`）。
- **part 生命周期**：`ensure_item_added` 每个 item 只发一次 `output_item.added`，工具名为空时**暂缓**开场而不写空串（`:199-257`，`:229-249`）；`ensure_part` 每个 `(item,part)` 只发一次 `content_part.added` 并按 Text/Refusal 选 payload（`:259-309`）；`part_end` 只对 `started && !done` 的 part 发 `*.done`+`content_part.done`（`:751-817`），item 收口前 `close_parts_for_item` 兜底关闭（`:959-1017`）。三重 `started/done` 守卫使 done 帧天然幂等。
- **快照对账**：`ItemSnapshot` 对 `message` 逐 part 做前缀对账（`:695-749`），`reasoning` 前缀延长（`:669-689`），`function_call` 走参数 assembly（`:520-637`）。冲突只记 `conflicts`（`:625-631`、`:717-721`），不改已发字节。终态快照里 id 未在 `output` 出现过的 item 才补发（`:1326-1336`），避免重复。
- **`sequence_number`**：客户端帧自带单调序号，由 `push` 在每次编码前写入并自增（`:109-115`）；它只用于客户端侧排序，与上游 `sequence_number` 无关——上游那个值由解码层读出后交给 `SourceObserver` 做重放识别（`decode/mod.rs:78-80`、`source.rs:467-494`）。

## 5. 工具参数对账：只延长已提交前缀

纯函数 `reconcile_arguments(committed, snapshot)`（`ir.rs:263-280`）给四种结论：`Duplicate`（一致）、`Extension{suffix}`（快照严格延长）、`Snapshot{arguments}`（原本为空）、`Conflict{committed,snapshot}`。

`ToolCallAssembly`（`ir.rs:172-260`）持有 `received`（已收到）、`committed`（已推送长度）、`snapshot`、`conflict`：

- 开场帧自带参数经 `seed_opening` 直接记入 `received` 并算已提交（`ir.rs:199-204`）；`push_delta` 只往已接收缓冲追加，由调用方 `mark_committed` 把已提交前缀推进到当前长度（`:206-213`）。
- `reconcile_snapshot` 用**已提交前缀**对账，不拿未提交字节（`ir.rs:232-239`）；冲突落 `conflict`。
- 终值 `final_arguments`：冲突时返回已提交前缀，否则优先权威快照（`ir.rs:242-249`）；`final_object` 在参数不是完整合法 JSON 时返回 `None`，拒用 `{}` 掩盖残片（`:253-259`）。

`ClientStream` 的 `ToolCallLedger` 记 `(candidate,index)` → **已接收参数全文**（`client_stream/mod.rs:247-286`），不是长度；`repair_tool_arguments`（`:377-434`）对 done 帧参数按同一纯函数分流：`Duplicate` 丢弃、`Extension` 只补后缀、`Snapshot` 补整段（仅在账本为空时成立，即「一个增量都没推过才补参」）、`Conflict` 只计数并保留已提交前缀（`:419-423`）。**opaque 事件本身始终原样保留**（`:426-428`），客户端状态机还要用它判定收口。Responses 目标侧的同款对账在 `item_snapshot`：只有 `Extension`/`Snapshot` 才推一个 `function_call_arguments.delta` 并 `mark_committed`，`Duplicate` 静默、`Conflict` 记诊断（`responses_target.rs:580-634`）。

四种前缀形态的判定差异，用 `committed = "{\"a\":"`、`snapshot = "{\"a\":1}"` 走一遍：

| 场景 | `committed` | `snapshot` | 结论 | 输出 |
| --- | --- | --- | --- | --- |
| 上游只发增量 | `{"a":` | `{"a":1}` | `Extension{"1}"}` | 只补 `1}` |
| 上游只发 done 帧 | `""` | `{"a":1}` | `Snapshot{"{\"a\":1}"}` | 补整段 |
| done 帧与增量一致 | `{"a":1}` | `{"a":1}` | `Duplicate` | 不补 |
| 上游改写已提交前缀 | `{"a":2}` | `{"a":1}` | `Conflict` | 不补，保留 `{"a":2}` |

`Extension` 只可能出现在严格前缀关系下（`ir.rs:270-273`）；`Conflict` 时 `final_arguments()` 固定返回已提交前缀（`ir.rs:242-249`），因此客户端不会收到两个版本拼接成的非法 JSON。Responses 侧 `item_end` 还会在终值不是完整 JSON 时发 `invalid_tool_arguments` 错误帧并跳过该 item（`responses_target.rs:850-867`）。

## 6. `StreamAggregator`（聚合与缓存装配）

`semantic/stream/aggregator.rs:27-36`：聚合到 `SemanticResponse`；`tool_positions` 只是 `(candidate,语义 index) → tool_calls 下标`。

- **幂等键 = 工具调用 id**：`ToolCallStart` 按 `existing.id.local == call.id.local` 复用下标，不命中才 push（`:203-218`）；重复开场不会产生第二个工具。
- **`PartStart` 赋值（覆盖）**（`:107-120`），**`PartDelta` 对文本追加**，槽位不是文本则整体替换（`:121-137`）。
- **空占位替换不拼接**：`Parsed` 参数遇到空对象/空数组/null 占位（Anthropic `input:{}`）时整段替换为后续 fragment，避免拼出 `{}{"loc":"SF"}`（`:219-244`、`:530-537`）。
- **done 帧补参**：opaque 分支仅在参数**仍为空**时用完整参数补一次，绝不重复累加（`:270-287`）。
- **预算**：`with_budget(max_bytes)`（`:54-56`）；每事件按「内容字节 + `EVENT_OVERHEAD_BYTES = 128`」（`:39`、`:405-442`）累计，超限置 `suppressed` 并停止累积（`:78-92`、`:94-101`），快照也计入（`:328-331`）。调用方读到 `suppressed` 即不写缓存并记 `response_cache_suppressed`（`stream.rs:2392-2398`）；预算来源是 `response_cache.memory_max_bytes`（`stream.rs:814`）。
- **终态判定**：`finish()` 依 lifecycle 状态返回 `Err(Incomplete/Failed)`（`:315-323`）；`into_partial_response()` 不判终态但把「没收到 terminal」写成 incomplete 原因（`:387-401`），`StreamLifecycle` 负责终态字段唯一性与 `EventAfterTerminal`（`:447-522`）。
- **快照权威性**（`merge_snapshot`，`:328-383`）：Responses 快照解码出内容/工具/推理任一非空即视为权威，**整体替换**流式候选（避免 delta 与快照重复）；否则只借元数据（id/model/usage/finish），不覆盖已聚合内容。Anthropic `message_start` 快照只提供元数据与用量，且 `stop_reason` 仅在原值为显式字符串且当前无 finish 时才采纳（`:373-380`）。两条分支都受同一预算约束（`:328-331`）。

## 7. 合成 vs 解码：统一入口

| 函数 | 输入 | 实现 |
| --- | --- | --- |
| `synthesize_client_frames`（`synthesis.rs:404-410`） | 语义响应 | `ClientStream::for_synthesis(source)` + `encode_response` |
| `synthesize_client_response_frames`（`synthesis.rs:417-426`） | 客户端协议形态 JSON | `decode_client_response`（`semantic/mod.rs:113-140`）→ 语义响应 → 同上 |

`encode_response`（`client_stream/mod.rs:131-168`）先用 `response_to_events`/`response_to_updates` 把响应展开成事件，再喂同一组目标状态机；`incomplete` 只让 Responses 走 `finalize_incomplete`（`:154-165`）。`for_synthesis` 拒绝 embeddings/interactions（`:106-117`），`ensure_synthesizable` 对无法表达的 content part 显式失败（`:173-190`）。生产接线：上游 JSON→流 `stream.rs:1428`、缓存重放 `cache_replay.rs:34`。**不存在第二套帧生成器**，生产流与合成/缓存共用同一编码器。

两条附加约束：合成路径没有上游协议，只有完整响应，所以 `for_synthesis` 与 `build_client_stream` 共用 `inner_for_protocol` 的分派（`:67-80`、`:119`），但 `encode_response` 必须自行收口（生产路径的收口由 `stream.rs` 调 `finalize*`）。所有出帧都经 `note_frames` 做聚合名回写（`client_stream/mod.rs:518-525`），合成帧同样会被改写，避免「流式改了、缓存重放没改」的名称漂移。

## 8. 解码层必须无状态

`decode_upstream_frame(protocol, &SseEvent) -> DecodedFrame` 是纯函数，也是唯一生产解码入口（`decode/mod.rs:44`）。因此**跨 SSE 事件的去重不能放在解码层**：解码器看不到上一帧。跨事件状态只能落在三处——`SourceObserver`（序列水位/重放指纹，`source.rs:467-494`）、`ClientStream` 公共层（`ToolCallLedger`，`client_stream/mod.rs:247-286`）、各客户端状态机内部（`responses_target.rs` 的 `item_for_key`/`items`）。把 trait 改成 `&mut self` 需改动四个协议适配器并修改 trait 契约，故不做；解码层的职责止于「这一帧能表达什么」。

具体后果：同一条 `function_call` 会在 `output_item.added` 与 `output_item.done` 各出现一次，解码层只能对两次都如实产出（`decode/responses.rs:70-133`）；「只下发一次开场、参数不重发」必须由有状态的一端保证——Responses 走 `allocate_item` 的键复用 + `ToolCallAssembly`，其余协议走 `ToolCallLedger`。若把去重塞回解码层，同一帧的 `events`/`updates` 会与 `SourceObserver` 看到的字节流不一致，Received 计数与续写前缀都会失真。

## 9. 工具名编码与 finish 单表

- **工具名可逆编码**（`semantic/tool_names.rs`）：合规名直通；否则逐字符编码——字面 `_` → `_5F_`，`\u{00}`–`\u{FF}` 非法字符 → `_HH_`，更大码点 → `_HHHH_`；Gemini 首字符不合法时前置 `_`（`:46-76`）。长度上限 `ANTHROPIC_MAX = 128`、`GEMINI_MAX = 63`，超长只截断（`:13-14`、`:68-75`）。`desanitize` 单遍扫描，先试 2 位再试 4 位十六进制，非编码形态原样通过，因此可无条件用于响应侧（`:81-110`）。编码侧调用见 `anthropic.rs:656`、`gemini.rs:749/782/818`，解码侧 `anthropic.rs:307`、`gemini.rs:267`、`stream/decode/anthropic.rs:62`。
- **finish 单表**（`semantic/finish.rs`）：入向 `from_openai`/`from_anthropic`/`from_gemini`（`:13/:34/:60`），出向 `to_openai_chat`/`to_anthropic`/`to_gemini`/`to_responses`（`:81/:94/:106/:119`）。全部经 `FinishReason` 中转，未识别原值落 `Opaque(raw)` 并伴随 `UnmappedEnum` 诊断，不做协议间直传。
