# 选路与候选计划

> 蒸馏自 [reference/03 §8–§9](../reference/03-网关协议与路由.md)（权威契约与类型表在该处），实现以 `wr-server/src/gateway/forward/`、`wr-domain/src/routing/` 为准。本文只写「请求准入 → 模型名解析 → 选路 → 聚合展开 → attempts 计划」的当前机制；重试推进、回退分类、熔断、并发与凭据池见 [韧性与凭据](./韧性与凭据.md)，前缀钉扎的成本语义见 [成本节省与响应缓存](./成本节省与响应缓存.md)，modelGroups 配置字段语义见 [reference/04](../reference/04-功能与兼容性.md)。白名单全等匹配与 attempts 类型表分别引用 reference/03 §8.3/§9.1，不在此复抄。

## 1. 链路总览

```
准入前置门（json.rs:40-375）→ 选择器解析（model_registry.rs:287-328）
→ attempts 计划（execution_plan.rs:59-113）→ 逐 attempt 选路/展开
（routing.rs:369-477）→ 逐候选改写 model 后发上游（json.rs:957-1003）
```

| 阶段 | 唯一实现入口 | 产物 |
| --- | --- | --- |
| 准入 | `forward/json.rs:40-375`；流式同序 `forward/stream.rs:383-520`（无幂等重放） | 放行，或带 `end_reason` 的拒行 |
| 解析 | `wr-domain/src/routing/model_registry.rs:287-328` | `RouteModelRef::Provider` / `Aggregate` |
| 计划 | `wr-domain/src/routing/execution_plan.rs:59-113` | `RouteExecutionPlan.attempts` |
| 选路/展开 | `wr-server/src/gateway/forward/routing.rs:369-477`、`model_groups.rs:111-138` | `(RouteCandidate, account_id)` 序列 |
| 消费 | `forward/json.rs:957-984`（流式另有同构循环） | 每次上游尝试的模型与账号 |

计划与选路分层的动因：attempts 是**跨模型**的主备序（`off`/`retry`/`model-chain`），选路是**单模型内**的候选序（粘性/聚合/显式 provider）。两层各自展开、互不复制，才能让 model-chain 的每个模型都重新走一遍聚合与粘性。

## 2. 准入前置门

非流式顺序（流式在 `forward/stream.rs:383-520` 同序接线压缩 → 上下文 → 白名单 → precheck → 策略，拒绝走 SSE 信封；流式没有幂等重放这一步）：

| 序 | 门 | 位置 | 拒绝结果 |
| --- | --- | --- | --- |
| 1 | provider 记录解析失败 | `json.rs:62-80` | 502 `no_provider` 审计行（`log_no_provider`，`:859-908`） |
| 2 | 选择器必须命中注册表 | `json.rs:104-146` | 400 `model_not_found` |
| 3 | token 压缩 | `json.rs:153-157` | 不拒绝，改写 payload |
| 4 | 上下文预筛（先估算 token） | `json.rs:162-196` | 400 `context_overflow`（所有 attempt 装不下） |
| 5 | API key 模型白名单 | `json.rs:200-230` | 403 `model_forbidden` |
| 6 | precheck 限流 / 预算 | `json.rs:233-276` | 429 `rate_limit_exceeded` / 402 `budget_exceeded` |
| 7 | 访问控制策略 | `json.rs:279-314` | 403 `policy_denied` |
| 8 | 幂等 | `json.rs:317-375` | 409 `idempotency_conflict`；`Completed` 直接重放旧体 |

- **压缩先于估算**：`compress_request_body` 先改写 `payload`（`json.rs:153-157`），随后 `estimate_tokens(&payload)`（`:162`）才估 prompt；顺序反了会把被压缩内容按原量计入上下文门。
- **模型名先解码再解析**：Claude Desktop 的十六进制模型名在准入最前解码，普通名字恒等（`json.rs:47-51`）；之后的选择器解析、白名单、策略都基于解码后的名字。
- **上下文预筛按 attempt 剔除**：`context_prefilter_plan` 保留能装下估算 token 的 attempt（`cache_io.rs:143-156`）；全被剔除即 400，不发起必败上游调用（`json.rs:164-196`）。
- **限流不回滚、预算回滚**：固定窗口计数先 `increment` 再比 `limit`，被拒请求吃进窗口的量保留（`limits.rs:20-21`、`:271-293`）；预算则先 `add_cost`，超限后用 `add_cost(-cost)` 冲销（`:189-226`）。API key 规则不受 `precheck.enabled` 门控，global 规则受（`:172-188`）。
- **白名单是全等匹配、无 glob**：只比客户端原始请求名（`requested`）与条目，trim + lower 后全等（`cache_io.rs:234-281`）；比较前不做逗号→斜杠归一化，条目需与请求原串同形（只容大小写/空白差异）。白名单为空或内部身份（`key_id` 空）放行（`:239-241`、`:268-270`）。
- **两个门看不同的名字**：白名单用 `client_requested_model`（原始 `Provider/模型` 或 `wrouter/聚合名`，`json.rs:58`、`:200`）；访问控制用 `model`——显式 provider 已被剥成裸模型名，聚合保留 `wrouter/聚合名`（`json.rs:86-92`、`:279-286`）。
- **顺序决定错误优先级**：上下文门在白名单之前，所以「超长且模型被禁」的请求得到 400 `context_overflow` 而不是 403；白名单在 precheck 之前，被禁请求不会先消耗限流窗口（`json.rs:162-230`）。
- **拒行审计口径**：上表除第 3 行（压缩，不拒绝）外的拒绝分支都以 `provider: None` 落一条 `RequestLogEvent`，`end_reason` 区分原因；这类行留在 `request_logs` 供审计，但 `provider` 归一成 `"unknown"` 后**不进任何统计聚合**（`usage_store.rs:8-12`、`:1460-1463`）。
- 幂等 `Completed` 重放不落新日志（`json.rs:363-371`）；`PENDING` 冲突写 409（`:351-361`），否则登记 pending（`:374`）。响应缓存精确键命中在幂等之后（`:380-461`），属节省链路，不在本文展开。

## 3. 模型名 → Provider 解析

**选择器规范化**（`model_registry.rs:83-100`）：trim 后空/全空白 → `None`；**首个逗号**仅在 `0 < idx < len-1` 且两段非空时转成 `/`，逗号在首/尾不算分解信号。`parse_provider_model_selector` 再按**首个 `/`** 分解，两段非空才命中（`:103-115`）。

`resolve_with_provider` 的顺序即代码里的 `if` 顺序（`:287-328`）：

| 步 | 规则 | 位置 |
| --- | --- | --- |
| 1 | `Provider/模型`：`find_provider` 命中别名，且模型在 `provider.models` 内大小写不敏感精确匹配 | `:294-300` |
| 1.5 | `wrouter/<聚合名>`：前缀 `eq_ignore_ascii_case("wrouter")`，聚合名小写查表且 `group.enabled` | `:302-318` |
| 2 | 显式 provider 提示下的域内匹配（内部编译/规则目标用） | `:320-326` |

- provider 别名 = `name` / `id` / `provider` 三键 trim 小写，加 `provider_runtime_id` 小写（`:176-189`）；`find_provider` 先 `provider_selector_base` 剥 `::<内部后缀>`，仅当后缀命中 `PROVIDER_INTERNAL_PROTOCOLS` 白名单才剥（`:28-34`、`:56-68`、`:335-344`）。
- 步 1 返回的是 `ProviderModelRef`，`model` 取配置里的原始大小写形态，`canonical_selector = <provider name>/<model>`（`:193-208`、`:227-239`）。
- **网关接线**：`resolve_client_prefix` 只在模型名含 `/` 时查注册表；命中 `Provider` 才剥离前缀并回填 `payload["model"]`（`forward/routing.rs:12-26`、`json.rs:86-92`）。聚合名不在 `route_target` 上，而是经 `build_fallback_plan` 落到首个 attempt 的 `target`（`json.rs:147`、`:390-395`）。
- 分解只认**首个** `/`：provider 段不能含 `/`，模型段可以（`model_registry.rs:103-115`）；合法分解还必须 provider 别名命中且模型在 `provider.models` 内，任一不满足就继续走后续级别，而不是报「部分命中」。
- 未命中选择器直接 400，不回退全池；裸模型名、裸聚合名与网关级别名通道均已下线（`json.rs:104-146`、`model_registry.rs:13-16`）。这是调用契约：所有请求必须显式写明目标，路由器不再「猜」。`select_provider` 对聚合引用也直接返回同一提示，因为它只接受 `RouteModelRef::Provider`（`routing.rs:47-51`）。

## 4. 选路四步与健康门

真实调用层级是：`route_candidates_for_attempt` 是统一管道（`forward/routing.rs:369-477`），内部依次做四件事，而不是四个平级调用：

| 步 | 函数 | 位置 | 何时生效 |
| --- | --- | --- | --- |
| 1 | `resolve_pinned_target` | `routing.rs:155-216` | 非聚合请求且全局 `prefixPin` / `stickySession` 开启 |
| 2 | `group_sticky_hit` | `routing.rs:307-342` | 仅 `ModelGroupStrategy::Sticky` 且会话键存在 |
| 3 | `expand_group_candidates` | `model_groups.rs:111-138` | 聚合请求 |
| 4 | `select_provider` | `routing.rs:40-66` | 非聚合且粘性未命中，仅显式 `RouteModelRef::Provider` |

- 步 1 内部顺序是**前缀钉扎 > 会话粘性**：钉扎命中但健康门失败会删钉扎并直接返回 `None`，不降级到会话粘性（`routing.rs:166-188`）；会话粘性命中要求 `entry.model == attempt_model`，否则删除绑定（`:200-213`）。钉扎/粘性命中时只返回**一个**候选，不再展开候选链（`:401-410`）——粘性是优化，命中即信任健康门。
- `select_provider` 是兜底而不是健康过滤：它只解析出 provider 引用，账号注入在 `route_candidates_for_attempt` 内完成（`routing.rs:459-472`）。如果这里就失败（provider 已被删配置），返回 `RoutingError` 文案，上层作为该 attempt 的 `last_error` 推进（`json.rs:979-984`）。
- **钉扎健康门** `pin_target_checked`（`routing.rs:82-113`）：provider 存在 + `enabled` + 熔断未开 + 能服务当前模型（`models` 空 / 含该模型 / 含 `"*"`，`:73-77`）+ 指定账号存在、`enabled`、未按模型冷却。任一失败返回 `None`，读取方释放绑定（`:179-185`、`:212-213`）。
- **聚合 sticky 健康门**（`routing.rs:321-339`）：目标仍在组内且 `enabled` + provider 存在 + `enabled` + 熔断未开；不健康即 `sticky_remove` 后返回 `None`（`:340`）。
- **聚合候选健康门**（`model_groups.rs:121-131`）：provider 存在 + `enabled` + 熔断未开；不查账号、不查模型白名单。全部被过滤 → 空候选 + 明确错误串（`routing.rs:442-450`），上层记 `last_error` 推进下一 attempt，全链耗尽才 502（`json.rs:979-984`、`:531-546`）。
- **单 provider 显式路径没有选路期健康门**：`select_provider` 只按 `id`（回退 `name`）在快照里命中，不检查 `enabled`（`routing.rs:52-62`）；熔断在候选循环发请求前复查（`json.rs:1006-1011`）。聚合请求跳过储蓄粘性/钉扎，因为绑定按实际模型记账、与聚合名口径不一致（`routing.rs:381-387`）。
- **模型匹配口径不同**：解析层 `configured_provider_model` 大小写不敏感（`model_registry.rs:193-208`），粘性健康门 `provider_serves_model` 用大小写敏感精确 `==`（`routing.rs:73-77`）；正常路径下 `entry.model` 与 `attempt_model` 都取自配置原串，口径差异只在配置串被改写时才可能暴露。
- 上游请求体的 `model` 必须是**裸模型名**：`upstream_model_name` 对有 `ProviderModelRef` 的 attempt 取 `reference.model`（`routing.rs:354-361`）；每个候选发请求前再按候选实际模型重写 `payload["model"]`（`json.rs:997-1003`），保证 model-chain 项不会把内部选择器发给厂商。
- **门分层但不作为承诺**：粘性/钉扎与聚合的健康门都只保证「不比正常链更差」——失败就释放绑定回到后续步骤；聚合全不可用则明确报错，绝不静默换到全池（`routing.rs:304-306`、`:340`、`:442-450`）。

## 5. 聚合展开

`sequence_for_strategy`（`model_groups.rs:37-80`）先 `targets.filter(enabled)`，再按 `priority ASC` **稳定排序**（同 priority 保持配置顺序，`:58-60`），层内按策略：

| 策略 | 行为 | 位置 |
| --- | --- | --- |
| `first` | 层内全部保留，按层序逐个尝试（严格主备） | `:61-63` |
| `weighted` | 每个 priority 层抽一个，层序=主备序，层内才是负载均衡 | `:64-79` |
| `sticky` | 命中目标置顶，其余按配置顺序，剔除**同 provider** 的其余目标 | `:42-56` |

- `weighted` 的抽取 `pick_weighted`（`:84-103`）：权重先 `max(0.0)` 夹紧；层内权重和 ≤ 0 → 取层内第一个（`:91-94`）；否则 `point = rng().clamp(0,1) × total` 逐项减权，落点命中（`:95-102`）。例：同层权重 3 与 1，`r = 0.9` → `point = 3.6`，减去 3 后仍 ≥ 0，再减 1 落负 → 命中第二个（单测 `model_groups.rs:232-269`）。
- `sticky` 命中分支**提前返回**，不再做 priority 分层；未命中（或无会话键）时落到与 `first` 相同的分层序列（`:43-63`）。
- 展开后再逐目标过健康门，产出 `RouteCandidate { provider, model }`（`model_groups.rs:30-34`、`:111-138`）。聚合请求**不追加** provider 级 fallback 链，targets 本身就是候选序（`routing.rs:425-426`）。
- 组内每个候选都是「主候选」：逐个注入账号凭据（`routing.rs:427-440`），各自携带实际模型名，失败推进由候选链负责（见 [韧性与凭据](./韧性与凭据.md)）。

## 6. 粘性三张 TTL 表

三张表都是进程内 TTL 表，重启清空；键空间互不碰撞（`session_affinity.rs:1-15`、`gateway/mod.rs:160-165`）。

| 表 | 键 | 值 | TTL | 容量 |
| --- | --- | --- | --- | --- |
| 会话粘性 | K4 会话键（`extract_session_key`） | `(provider, model, account)` + 缓存观测 | `savings.sticky.ttlSecs`，默认 900s | `STICKY_MAX_ENTRIES = 1000` |
| 前缀钉扎 | `prefix_pin_key` 的 64 字符 SHA-256 hex | `(provider, account)`，不含 model | `PREFIX_PIN_TTL_MS = 300_000` 固定 | `PREFIX_MAX_ENTRIES = 1000` |
| 组粘性 | `model-group:{group_id}:{session_key}` | `(provider, model, account)` | 与会话粘性同源 | 复用会话表，1000 |

- 键提取：会话键优先 `x-claude-code-session-id` → `x-session-id` → `x-request-id`（头名大小写不敏感），否则取首条 `user` 消息内容的 SHA-256 前 16 hex，空内容视为无（`wr-domain/src/gateway.rs:136-172`）。前缀键是「最后一个带 `cache_control` 断点的 message（含）之前的 messages + tools」的 SHA-256，断点只由 messages 里的 `cache_control` 决定、tools 恒参与哈希但不驱动截断，无断点返回 `None`（`cache_prefix.rs:31-55`）。
- TTL 装载：会话表与组表随 `savings.sticky.ttl_secs × 1000` 热刷新（`gateway/mod.rs:243-247`），默认 900s（`config.rs:573-585`、`session_affinity.rs:115-120`）；前缀表 TTL 是常量、不同步配置（`session_affinity.rs:23`、`:228-238`）。
- 惰性过期：`get` 发现 `expire_at_ms <= now` 即删条目并返回 `None`（`session_affinity.rs:74-82`）；`bind` 写入 `now + ttl`，容量超限按插入序 FIFO 淘汰最旧，重绑先摘旧占位再入队（`:84-96`），所以淘汰序不会误删新值。
- 三张表都是可丢的运行态：不用持久化、不引入 LRU crate，容量上限 + 读取时过期删除就足以防无界增长（`session_affinity.rs:11-15`、`:65-72`）。重启清空与凭据池冷却态同一立场——单机可接受，重启后按正常链重新学习。
- **只由成功写**：非流在最终 `status < 400` 时写 `bind_savings_targets` 与 `bind_group_sticky`（`json.rs:1486-1517`）；流式在成功终态写（`stream.rs:1530-1556`、`:2361-2390`）。健康门失败/模型不匹配会释放（`routing.rs:179-185`、`:212-213`、`:340`）；流式中途断流或 EOF 不完整也释放会话/前缀/组粘性绑定（`stream.rs:958-964`、`:2247-2253`，统一入口 `routing.rs:274-298`）。
- **冷判据**（`routing.rs:120-146`、`session_affinity.rs:283-294`）：`cold_after = cacheColdSecs × 1000`（默认 300s，`config.rs:576-585`），≤0 关闭判据；只有协议族**确实上报缓存**才判（`reports_cache_usage` 当前仅 Anthropic，`wr-domain/src/provider.rs:54-56`），不上报的族一律保留。满足「`hits >= STICKY_CACHE_MIN_HITS`（=2）且 `cache_read_tokens == 0` 且绑定已过冷窗口」→ 不值得保留，删绑定落正常链；其余保留。
- `hits` 是**成功重复绑定**次数：同 `(provider, model, account)` 重绑累加 cache token、`hits + 1`，保留首次 `bound_at_ms`（冷窗口基准不刷新）；换目标则统计清零重来（`session_affinity.rs:162-199`）。组粘性用无观测的 `sticky_bind` 写，cache 统计恒为默认（`routing.rs:501-514`）。
- **冷判据只作用于会话粘性**：聚合请求根本不走 `resolve_pinned_target`，组粘性条目不累计缓存统计，前缀钉扎条目不含 model 也不累计统计，判据不会误杀它们（`routing.rs:120-146`、`:381-387`、`:501-514`）。

## 7. attempts 生产与 clamp

`create_route_execution_plan`（`execution_plan.rs:59-113`）只消费全局 `router_fallback`（`:116-118`），`primary = normalize(body_model) || normalize(primary_model)`（`:66-67`）：

| 模式 | attempts | 位置 |
| --- | --- | --- |
| `off` 或无请求体 | 1 个，`primary` | `:70-76` |
| `retry` | `retry_count + 1` 个，全部指向同一 `primary` | `:78-92` |
| `model-chain` | `primary` + `fallback.models` 保序去重后逐个解析 | `:94-112` |

- `clamp` 口径：`clamp_finite` 对值取 `trunc()` 后夹 `[0, ROUTER_FALLBACK_MAX_RETRY_COUNT]`，常量 **9999**（`execution_plan.rs:19-27`、`contracts.rs:331`）；非数值/非有限回退 0。配置侧 `retryCount` 解析失败也回退 0（`contracts.rs:367-370`），所以 attempts 上限是 10000。
- `model-chain` 的项先 trim、丢空、保序去重（`execution_plan.rs:30-42`）；编译配置时已按 `model-chain` 模式剥离未在注册表配置的模型（`config_compiler.rs:62-76`）。每项经 `registry.resolve` 解析成 `target`（`:45-56`），解析不到不报错，运行时该 attempt 无候选再推进。
- 例：`retry_count = 2` 且 `mode = retry` → 3 个 attempt 全部 `primary`（单测 `execution_plan.rs:183-198`）；`primary = P1/m1`、`fallback.models = [P1/m2, P1/m1, P1/m2]` → attempts 为 `[P1/m1, P1/m2]`（`:200-214`）。
- attempt 的 `target` 有两种来源：显式前缀请求的 `target` 通常为 `None`，provider 引用由 `route_target` 携带（`json.rs:962`、`:86-92`）；聚合请求的 `target` 是 `Aggregate`，由计划解析得到（`json.rs:390-395`）。`route_candidates_for_attempt` 用 `attempt_target.or(route_target)` 统一消费（`json.rs:962`）。
- 计划消费：每个 attempt 先写回 `attempt_model`，再走统一选路管道；候选为空则记 `last_error` 进下一 attempt（`json.rs:957-984`）。三层重试的总预算跨层共用（`json.rs:951-956`），细节归 [韧性与凭据](./韧性与凭据.md)。
- `off` 模式即使 `primary` 为 `None` 也产出 1 个 attempt（`execution_plan.rs:70-76`）；消费侧 `attempt_model = plan.model.unwrap_or(model)` 回落到原始请求名（`json.rs:957-961`），选择器仍解析不到时由该 attempt 返回无候选。
- `RouterFallbackMode` / `RouteAttemptPlan` / `RouteExecutionPlan` 等类型表见 reference/03 §9.1（`contracts.rs`），本文不另立权威。

## 8. 边界与不做

- **不做全池兜底**：未命中选择器 400（`json.rs:104-146`），聚合目标全不可用 502（`routing.rs:442-450`），只有 `model-chain` 的显式配置能跨模型推进。
- **不做 provider 级 fallback 链**：候选只来自粘性命中（单项）、聚合 targets 或显式 provider（单项）（`routing.rs:399-410`、`:425-426`、`:462-472`）。
- **不在这里解释韧性**：同 provider 重试、候选链回退、重试预算、熔断开合、并发许可与凭据池轮转属于 [韧性与凭据](./韧性与凭据.md)；本文只说明选路产出什么候选序列。
- **不在这里解释成本语义**：前缀钉扎为什么省钱、粘性收益如何计量属于 [成本节省与响应缓存](./成本节省与响应缓存.md)；本文只说明三张表的键、TTL、写入与释放条件。
- **不重复配置字段契约**：modelGroups 的 `strategy/priority/weight/enabled` 字段语义与写入约束见 [reference/04](../reference/04-功能与兼容性.md)；本文只描述运行时展开。
