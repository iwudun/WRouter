# 成本节省与响应缓存

> 蒸馏自 [reference/03 §13.3](../reference/03-网关协议与路由.md)（落点表）、分层前的缓存/聚合预算机制（现 reference 只留摘要）与 [reference/02 §4](../reference/02-架构设计.md)（`savings_events` / `response_cache` 两表）。**以代码为准**，本文路径相对 `backend/crates/`。会话粘性选路见 [选路与候选计划.md](./选路与候选计划.md)；节省/用量的统计聚合与分位是另一主题，本文只指记账落点。

## 1. 动作解析：规则域下线后只剩全局一层

`ResolvedSavings { compression_tier, sticky_session, prefix_pin, response_cache }`（`wr-server/src/gateway/savings.rs:13-20`），默认全关（`:22-31`）；`resolve_savings` 直接读 `SavingsConfig`，无规则覆盖层（`:34-48`）。压缩 `mode` 只认 `"auto"` / `"full"`，**其余一切值（含缺失/坏值）→ `Off`**（`:37-41`）；档位枚举 `Off/Auto/Full` 在 `wr-domain/src/routing/contracts.rs:310-324`。

| 动作 | 配置键 | 默认 | 消费点 |
| --- | --- | --- | --- |
| 压缩 | `savings.compression.mode` / `.thresholdTokens` | `off` / `32_000`（`wr-infra/src/config.rs:533-539`） | `forward/json.rs:153-157`、`forward/stream.rs:383-387` |
| 前缀钉扎 | `savings.prefixPin.enabled` | `false` | `forward/routing.rs:166-188`（读）、`:255-266`（写） |
| 响应缓存 | `savings.responseCache.enabled` | `false`（`config.rs:553-563`） | `forward/json.rs:401-406`、`forward/stream.rs:547-552` |

解析发生在两条转发管线的入口（`json.rs:149`、`stream.rs:380`），此后同一份 `resolved` 贯穿选路、出站、回写与记账。

## 2. 三方门控的顺序与相互作用

一次非流请求的实际次序（流式同构，行号见括注）：

1. **原始入站快照**：会话键、客户端指纹在改写前取（`json.rs:34-45`）；`provider/model` 选择器分解后就地把 `payload.model` 换成裸模型名（`:86-92`）。
2. **压缩**：对 `payload` 就地改写，产出 `CompressionReport`（`json.rs:153-158` / `stream.rs:383-388`）；同一估算器 `estimate_tokens` 随后驱动上下文预检（`json.rs:162-163`）。
3. **响应缓存键 + 命中判定**：键在**压缩之后**的 `payload` 上算（`json.rs:401-406` / `stream.rs:547-552`）；命中即落日志、回写头、返回，**不进入选路**（`json.rs:407-461` / `stream.rs:553-571`）。
4. **前缀钉扎**：只在未命中后的候选选路里查表（`routing.rs:387-411` → `resolve_pinned_target:155-216`，钉扎分支 `:166-188`）。
5. **成功回写**：`status < 400` 才写缓存（`json.rs:651-663`）、才绑钉扎（`json.rs:1488-1507` → `routing.rs:255-266`）、才记压缩账（`json.rs:665-667`）。

| 组合 | 当前行为 | 依据 |
| --- | --- | --- |
| 压缩 × 钉扎 | **可共存**：压缩强制不压的段（system + 断点前缀）正是钉扎键的覆盖段，断点后改写不影响键 | `compression/mod.rs:177-180`、`cache_prefix.rs:36-55` |
| 压缩 × 响应缓存 | **有张力**：键含全量 `messages` 且在压缩后计算 → 档位切换或引擎生效差异即换键 miss | `gateway.rs:241-243`、`json.rs:153-157`→`:403` |
| 缓存命中 × 钉扎 | 命中直接返回，钉扎表既不读也不写（省整次上游调用，上游 prompt cache 无从谈起） | `json.rs:451-460`、`cache_replay.rs:97-100` |
| 缓存命中 × 压缩账 | 压缩管线已执行并进日志 extra，但**只记 `response_cache` 一笔账**，避免双账 | `cache_io.rs:187-203`、`json.rs:415-418`、`routing.rs:531-539` |
| 聚合请求 | 响应缓存与前缀钉扎**双双排除**（键含聚合名而实际候选模型可变；钉扎绑定按实际模型记账口径不一致） | `json.rs:386-406`、`stream.rs:546-552`、`routing.rs:381-387` |
| stateful 请求 | `previous_response_id` / `conversation` / `conversation_id` 任一存在 → 无键，不缓存 | `gateway.rs:200-211`、`:222-224` |

`x-wr-no-cache: true`（大小写不敏感、trim 后比较）是客户端旁路：键直接为 `None`，**读与写同时关闭**（`json.rs:383-385`、`stream.rs:543-545`）。幂等重放缓存（`idempotency`，`json.rs:318-375`）是另一套键与门，不与本文混用。

## 3. 压缩：档位、缓存感知门、保真门

### 3.1 档位与触发

入口 `compress_request_body(body, tier, threshold_tokens)`（`wr-domain/src/compression/mod.rs:157-211`）：`Off` 或 body 非对象 → `None`（未进管线，日志 extra 为空）；`Auto` 且 `estimate_tokens(body) <= threshold` → `Some(report)` 且 `skipped_reason = "below-threshold"`、`engines` 为空（`:162-174`）；`Full` 恒进引擎链。估算口径 `estimate_tokens = JSON 文本字节数 / 4`（`:150-152`，CJK 偏差只影响触发时机）。

### 3.2 缓存感知门（哪些段永不压）

`CompressionCtx { protect_system, protect_messages_up_to }`（`:36-45`）在管线里**恒置 `protect_system = true`**，`protect_messages_up_to = last_breakpoint_message_index(body)`（`:177-180`）——即不再按「目标供应商是否有前缀缓存能力」分支，内建协议一律视为有（`:38-40`）。落地在槽位遍历器：system 段整段跳过（`compression/engines.rs:51-65`），`messages[..=bound]` 逐条跳过（`:70-77`）；断点定位是**整条消息任意深度**递归搜 `cache_control`（`cache_prefix.rs:18-29`、`:59-64`），tools/system 上的断点不驱动截断。

三个内建引擎按 `stack_priority` 升序叠加（`mod.rs:181-186`），全部无损、不做 LLM 摘要/语义剪枝（`:18-19`）：

| 引擎 | 优先级 | 目标槽位 | 触发常量 |
| --- | --- | --- | --- |
| `whitespace-lite` | 10（`engines.rs:165-167`） | messages + tool_results | 文本 ≥ `WHITESPACE_MIN_CHARS = 64` 字符（`:158`）；代码围栏内不动 |
| `table-columnar` | 20（`:265-267`） | messages + tool_results | ≥ `TABLE_MIN_ROWS = 3` 行（`:258`） |
| `tool-output-trim` | 30（`:416-418`） | 仅 tool_results | > `TRIM_TRIGGER_CHARS = 6_000` 字符时保头尾各 `TRIM_KEEP_CHARS = 1_600` + 省略桩（`:408-409`、`:427`） |

### 3.3 保真门：存在性语义与回退

每引擎**先克隆快照再 apply**，`changed && !vitals_preserved(snapshot, body)` → 整体回退该引擎改动并记 `skip_reason = "fidelity"`（`mod.rs:188-203`）。判定四类硬性不可丢集合（`compression/fidelity.rs:23-30`、`:75-84`）：

```
after.numbers ⊇ before.numbers  ∧  after.urls ⊇ before.urls
∧  after.keys ⊇ before.keys     ∧  after.fence_count >= before.fence_count
```

数字/URL/文本内 JSON key 用**存在性集合**而非计数多重集——列式引擎把重复 key 去重到表头是合法收益，逐项计数会误杀（`:11-12`、`:144-151`）；围栏只要求计数不减（配对被破坏即拒，`:136-141`）。正则在序列化全文上提取（`:32-46`、`:50-70`），故 `max_tokens` 这类结构数字与文本数字一视同仁。

**fail-open 的真实落点**：`serde_json::to_string` 失败 → `unwrap_or_default()` 得空文本 → 空集合 ⊆ 任何集合恒真 → 放行压缩（`:76-79`、`:48-49`）。注意 `:32-46` 的三个内置正则用 `expect("内置正则必然可编译")`，构造失败是 panic 路径而非放行；模块注释「正则构造失败 → 空集合」与实现不符，护栏语义只由序列化退化路径承重。

### 3.4 报告

`tokens_saved_estimate = (chars_before − chars_after) / 4`（`mod.rs:97-99`），`to_value()` 输出 camelCase（`skippedReason` / `engines[].skipReason` / `charsBefore` / `charsAfter` / `tokensSavedEstimate`，`:102-141`），经 `compression_extra_map` 挂到调用日志 `extra.compression`（`routing.rs:531-539`）。引擎级 skip 词表：`fidelity` / `no-gain` / `parse-failed` / `not-a-tool-result` / `below-min-length`（`mod.rs:52-54`、`engines.rs:483-487`）。

## 4. 前缀钉扎：键、TTL、容量

键 = 「最后一个携带 `cache_control` 的消息（含）之前的全部 messages + tools」紧凑序列化后的 SHA-256 全摘要 64 位小写 hex（`wr-domain/src/cache_prefix.rs:36-55`、`:68-75`）。无 `messages` 数组或无断点 → `None`（不钉扎）；**tools 恒参与哈希但不驱动截断点**，工具集变化必须 miss（`:48-51`）；断点后追加/改写消息不改键（`:130-140`）。

| 项 | 取值 | 位置 |
| --- | --- | --- |
| TTL | `PREFIX_PIN_TTL_MS = 300_000`（固定常量，不进配置、不随 `sync_runtime_config` 刷新） | `wr-server/src/gateway/session_affinity.rs:23`、`:234`；`gateway/mod.rs:241-247` |
| 容量 | `PREFIX_MAX_ENTRIES = 1000` | `session_affinity.rs:27`、`:236` |
| 条目 | `PrefixPinEntry { provider_id, account_id }`，**不含 model** | `:57-63` |
| 淘汰 | 插入序 FIFO（重绑先摘旧占位），读取时过期即删 | `:74-82`、`:84-96` |
| 时钟 | `now_ms() = wall_ms()`，与凭据冷却/缓存同源 | `:264-266` |

条目不含 model ⇒ 读取方必须自证目标能服务当前模型：健康门 `pin_target_checked` 校验 provider 存在 + enabled + 未熔断 + `provider_serves_model`（models 空或含 `*` 视为任意），指定账号还须 enabled + 未冷却（`routing.rs:73-113`）。门失败 → `prefix_remove` 并返回 `None` 落正常链，**不降级到会话粘性**（两表键空间不同，钉扎表已给出失效意见，`routing.rs:153-154`、`:180-185`）。写入只由成功响应触发（`routing.rs:248-266`）；断流/不完整终态显式释放（`routing.rs:286-290`，调用点 `stream.rs:958`/`:2247`/`:2542`）。表是进程内存态，重启清空（`session_affinity.rs:3-4`）。

与响应缓存的分工：钉扎省的是**上游 prompt cache**（同前缀粘同一 provider/account），响应缓存省的是**整次上游调用**；两者键空间、TTL、存储层完全独立，命中响应缓存时钉扎不参与（见 §2）。

## 5. 响应缓存：键、两层存储、命中重放

### 5.1 键构造与门

`response_cache_key(protocol, payload)`（`wr-domain/src/gateway.rs:220-254`）：先过 stateful 门（`:222-224`），再要求**显式数值 `temperature == 0`**——`as_f64() == 0.0`，省略 temperature 或字符串 `"0"` 一律无键（`:226-233`，宁可少命中不可错误命中）。键 = SHA-256(紧凑序列化 `{protocol, model?, messages?, top_p?, tools?}`)（`:234-253`）：

- `protocol` 进键：缓存值是**按客户端协议解码后的 JSON**，跨协议重放形状不安全（`:218-219`）；
- `tools` 进键：工具集变化必须 miss（`:247-249`）；
- `messages` 用解析后的 `Value` 序列化，天然与原请求空白/键序无关，数组语义序保留（`:239-243`）；
- 键在候选重写前算定：`payload.model` 此后会被逐 attempt/逐候选就地改写（`json.rs:963-964`、`:999-1003`），键仍用客户端解析出的模型名，且**不含 provider/account/candidate model**；
- 覆盖面缺口：`system`（Anthropic 顶层）、`tool_choice`、`max_tokens`、`stream` 都不进键（`:234-249`）——只改顶层 system 的两次请求共用条目；`stream` 不进键则使同一 body 的流式/非流式共用条目，重放形态由请求路径决定。

### 5.2 两层存储与预算

| 层 | 实现 | 默认上限 / TTL |
| --- | --- | --- |
| 内存 | `ResponseCache`（`Mutex<Inner>`，`HashMap` + 插入序 `VecDeque`） | 64 条 / 5 MiB / 1800s（`gateway/response_cache.rs:47-53`、`config.rs:553-563`） |
| 磁盘 | `response_cache` 表，`INSERT … ON CONFLICT DO UPDATE` + 惰性清过期 + 按 `created_at_ms DESC` 保留最新 N 条 | 1000 条 / 3600s（`wr-infra/src/sqlite/response_cache_store.rs:79-103`、`config.rs:560-561`） |

内存淘汰是**插入序 FIFO 而非 LRU**：`get` 不刷新 `order`（`response_cache.rs:76-86`），`put` 先摘同键旧值再入队尾，条数或字节超限即淘汰最旧（`:90-112`）；字节口径 = `payload.to_string().len()`（`:29-31`）。上限随配置刷新（`sync_limits`，`:128-130`，调用点 `gateway/mod.rs:249-252`）。读路径内存 → 磁盘，磁盘命中**晋升内存并按 `memory_ttl_secs` 重新计 TTL**（不保留剩余磁盘 TTL，语义近似，`forward/cache_io.rs:12-32`）；写路径两层都写，磁盘失败 `let _ =` 静默降级为仅内存（`:35-67`）。

### 5.3 写入路径：存语义聚合后的客户端 JSON

| 路径 | 写入条件 | 存什么 |
| --- | --- | --- |
| 非流客户端 | `response.status < 400` 且键存在（`json.rs:651-663`） | 解码后的客户端协议 JSON `body`（`:560-622`） |
| 流式客户端 + 非流上游（A6） | `resolved_savings.response_cache` 且键存在（`stream.rs:1566-1578`） | 同一份 `decoded` 客户端 JSON（合成帧由它派生，`:1428-1447`） |
| 流式客户端 + 流式上游 | 仅 `upstream_ok` 成功终态分支（`stream.rs:2315`→`:2388-2420`） | `StreamAggregator` 累积语义事件 → `into_partial_response()` → `synthesize_client_response(source, …)` 编码成客户端 JSON（`:2403-2417`） |

**绝不把原始 SSE 当 JSON 存**：缓存装配器只在有键时创建（`stream.rs:811-814`），喂料点是 `RecordEncoder`——仅 `observer.observe` 接受的事实才 push 事件并 merge 快照（`forward/record_encoder.rs:61-69`），重放/违规帧不进聚合器。缓存关闭时整条聚合与原始字节复制都不发生（`stream.rs:804-814`）。

### 5.4 命中回写与重放

非流命中直接返回缓存 JSON（`json.rs:451-460`）；流式命中走 `replay_cached_response`：`synthesize_client_response_frames(protocol, &hit.payload)` 先把客户端 JSON 解码回语义响应、再经**同一目标编码器**产帧（`forward/cache_replay.rs:34-50` → `wr-domain/src/semantic/synthesis.rs:417-427`、`:404-410`），逐帧 `delivery.emit`（`:58-66`）。解码失败或空帧 → warn `cache_replay_invalid` 并**按 miss 继续回源**（本请求会覆盖该条目），绝不把整段 JSON 塞进单个 `data:` 帧冒充合法流（`:39-50`、`:100`）。

| 回写头 | 值 | 位置 |
| --- | --- | --- |
| `x-wr-cache` | `hit`（未命中**不下发**该头） | `json.rs:455`、`cache_replay.rs:54` |
| `x-wr-cache-age-ms` | `now_ms − created_at_ms`（saturating） | `json.rs:450-456`、`cache_replay.rs:52-55` |
| `x-wr-cost-saved` | 写入时存的 `cost_usd`，`{:.6}` 格式化 | `json.rs:457`、`cache_replay.rs:56` |

命中计费 $0：日志 `with_usage(usage, 0.0)`、`end_reason = "cache_hit"`、extra 追加 `cacheSource = "hit"` 与 `costSavedUsd`（`json.rs:413-449`、`cache_replay.rs:28-33`、`:67-96`）；`usage` 从缓存 payload 的 `usage` 键归一化而来。流式头在首帧提交前经 `delivery.set_headers` 设置（`cache_replay.rs:53-57`）。

### 5.5 聚合预算与 suppressed

流式缓存装配复用 `response_cache.memory_max_bytes` 作预算（`stream.rs:809-814`）：`StreamAggregator::with_budget(max_bytes)`（`wr-domain/src/semantic/stream/aggregator.rs:54-56`），每事件权重 = 内容字节 + `EVENT_OVERHEAD_BYTES = 128`（`:39`、`:405-446`），快照按 `128 + json_weight(value)` 计（`:328-331`）。`reserve` 溢出或超预算即置 `suppressed` 并拒绝继续累积（`:78-92`），此后 `push` 直接返回（`:94-97`）。调用方见 `is_suppressed()` 为真 → **不写缓存**（绝不写截断结果）+ 低基数 warn 日志 `response_cache_suppressed`（target `wrouter.gateway.proxy`，字段 `request_id` / `protocol` / `budget_bytes`，`stream.rs:2392-2399`）。非缓存路径的 `new()` 不设预算，行为不变（`aggregator.rs:48-50`）。

## 6. 节省记账落点

两个写账函数都在 `wr-server/src/gateway/forward/cache_io.rs`，fire-and-forget（`tokio::spawn` + 忽略错误，度量非关键路径）：

- `record_compression_savings`（`:160-183`）：`kind = "compression"`，`tokens_saved = report.tokens_saved_estimate()`，`<= 0` 不写，`engine_breakdown = report.to_value()`；
- `record_cache_hit_savings`（`:187-203`）：`kind = "response_cache"`，`tokens_saved = usage.input_tokens + usage.output_tokens`（被免掉的整次用量）。

两者 `estimated_usd_saved` **恒 0.0**（2026-09-11 起只记 token 不记金额，`:158-159`、`:185-186`）；`x-wr-cost-saved` 头与日志 `costSavedUsd` 仍带原始成本，但不进事件表金额列。落库 `SqliteStore::record_savings_event`（`wr-infra/src/sqlite/savings_store.rs:39-63`，`actual_tokens_saved` / `skip_reason` 写 NULL），表定义 `wr-infra/src/sqlite/schema.rs:61`。`kind = "prefix_hit"` 是保留字面、**v1 不写**（上游缓存收益由 `request_logs.cache_read_tokens` 折算，避免双账，`savings_store.rs:10-12`）。三本账汇总口径见 `savings_summary`（`:67+`），本文不展开。
