# 服务生命周期：控制状态机与顺序停机

> 蒸馏自 [reference/02 §5.1](../reference/02-架构设计.md)（服务控制概览）与 [reference/07 §1.5.1](../reference/07-FAQ与已知限制.md)（「正在停止」≠「已停止」等用户语义）。用户三动作表以 reference/07 §1.5 为准、RPC 白名单与五点同步契约以 reference/02 §5 为准，本文不复制；SSE 帧契约见 `contracts/events-schema.json`。
>
> 行号基准：`lib.rs`、`service_control.rs`、`admin/*`、`gateway/*` 相对 `backend/crates/wr-server/src/`；`tests/*` 相对 `backend/crates/wr-server/tests/`；其余为仓库根相对路径。

## 1. 三个宿主，一条服务路径

CLI（`wr serve`）、systemd 单元、Tauri 桌面壳共用 `run_serve_with_shutdown`（`lib.rs:268-274`），停机信号由调用方注入：CLI 传 `shutdown_signal()`（SIGINT + SIGTERM，`lib.rs:221-253`）；桌面壳传窗口关闭驱动的 oneshot future（`desktop/src-tauri/src/backend.rs:94-99`）；回归测试可注入 `pending()` 永不触发、只靠页面 RPC 停机。

- 单一信号必须**显式广播**：原实现两个 server 各挂一个 ctrl_c 监听，抽成单一 future 后若不广播，只有一个面收到停机（`lib.rs:264-267` 注释）。现由 `stop_task`（`lib.rs:321-343`）把「外部注入信号」与「页面停机请求」汇成一路全局 watch `stop_tx`（`lib.rs:310`）。
- 启动装配完成后**双面 bind 快速失败**（`lib.rs:301-307`）：任一端口被占 → 整个启动失败；只有「暂停后恢复」才允许 bind 失败重试（§3）。
- systemd 宿主：单元 `ExecStart=/usr/bin/wr-backend serve …`（`packaging/wrouter.service:11`），SIGTERM 走同一 `shutdown_signal()`；`Restart=on-failure` + `RestartSec=3`（`12-13`）只兜崩溃，不复活主动停止（§8）。
- 桌面壳把后端跑在同进程独立线程 + 独立 tokio runtime（`desktop/src-tauri/src/backend.rs:75-99`）：后端有 SQLite 阻塞读、必须 multi_thread，独立 runtime 不与窗口事件循环抢线程（`backend.rs:7-11` 注释）。关窗口时 `BackendHandle::shutdown` 发停机信号并 join 后端线程（`backend.rs:44-51`），`Drop` 兜底（`54-58`）。

## 2. 控制通道：五路 watch 与托管判定

`ServiceControl`（`service_control.rs:91-106`）可克隆、克隆体共享同一组 `tokio::sync::watch` 发送端；由 `run_serve_with_shutdown` 创建（`lib.rs:320`），克隆注入管理面 `AdminState.control`（`lib.rs:89-95/386`）与网关面任务（`lib.rs:368`）。选型约束：零新依赖，只用已在 Cargo 里的 watch（`service_control.rs:9-10`）；watch 只保留最新值（`send_replace`，`service_control.rs:138`），适合意图/状态旗而非事件队列。五路通道（初值见 `service_control.rs:116-129`）：

| 通道 | 初值 | 写入方 | 读取方 |
| --- | --- | --- | --- |
| `gateway_enabled`（启停**意图**） | true | RPC `setGatewayEnabled`（`admin/service_control.rs:64`） | 网关面任务（`lib.rs:515/572`） |
| `gateway_running`（实际监听态） | false | 网关面任务（`lib.rs:552` 等） | `gateway_state()` 推导 |
| `gateway_error`（最近错误） | None | bind / serve 失败（`lib.rs:544/567`） | `gateway_state()`、`getRuntimeControl` |
| `stop_accepted`（停机**已受理**） | false | RPC `stopService` 即刻置位（`admin/service_control.rs:94`） | `stopping()` → 页面「正在停止」 |
| `stop_requested`（停机**请求**） | false | 延迟任务 / 外部信号 / 管理面死亡守护（§4/§7） | 网关面、SSE 收流、`stop_task` |

- `stopping() = stop_accepted || stop_requested`（`service_control.rs:200-202`）。受理与请求是**时间差**：受理立刻可见，请求等 HTTP 响应落地后才置位（§4）。
- `gateway_state()` 优先级 `error > stopped > starting/running`，按**意图**而非瞬时监听态推导（`service_control.rs:210-222`）——点「暂停」而监听尚未释放的一瞬间也报 `stopped`，避免界面闪回「运行中」；`setGatewayEnabled` 回执同口径（`admin/service_control.rs:73-74`）。典型投影（`getRuntimeControl` / `getGatewayStatus` 上报的就是它）：

| 场景 | enabled | running | error | `gateway_state()` |
| --- | --- | --- | --- | --- |
| 初始启动、尚未监听 | true | false | None | `starting` |
| 正常服务 | true | true | None | `running` |
| 已暂停 | false | false | None | `stopped` |
| 恢复中 bind 持续失败 | true | false | Some | `error` |
- 托管判定 `ManagedBy::from_env()`（`service_control.rs:76-86`）：`WROUTER_MANAGED_BY` 显式值（大小写不敏感，含 tauri/desktop/standalone/service 别名，`46-53`）> systemd 注入的 `INVOCATION_ID` > 默认 `process`。桌面壳置 `embedded`（`desktop/src-tauri/src/backend.rs:207-209`）；systemd 单元显式声明（`packaging/wrouter.service:26`，不依赖 user 单元下的 INVOCATION_ID 探测）。`canPause` 恒 true，`canExit`/`exitAction` 由托管方式推导（`admin/service_control.rs:42-45`）。

## 3. 网关面状态机（run_gateway_face）

网关面是独立 tokio 任务，不是与管理面并列的 server（`lib.rs:367-376` → `run_gateway_face`，`lib.rs:498-595`）。任务自身四态：

| 任务态 | 事件 | 动作 | 次态 |
| --- | --- | --- | --- |
| serving | 暂停意图 | `pause_tx` → drain ≤10s → 释放 3460 监听 | paused |
| paused | 恢复意图 | 重新 bind 3460 | 成功→serving；失败→bind-retry |
| bind-retry | 3s 到期 / 暂停意图 | 再 bind / 回循环头 while | 成功→serving；失败→bind-retry / paused |
| paused | `global_stop` | 直接返回 Ok（无在途、无需排空） | exited |
| serving | `global_stop` | `pause_tx` → drain ≤10s → 返回 Ok | exited |
| serving | server 自身结束 | Err 记 `gateway_error`；置 running=false | exited |

- **暂停 = 关 3460 监听**：触发 axum 优雅停机（`lib.rs:578`）→ `drain_gateway` 等 in-flight 收尾（暂停与停机共用同一 10s 上限，`lib.rs:579/588/602-624`）→ 释放监听，不占端口、不转发，客户端 connection refused；**管理面 3462 不受影响**，可看状态、改配置、点恢复。
- **恢复**：重新 bind；失败记 error、**3s 后重试**（`lib.rs:544-547`），管理面继续服务。
- **暂停态必须盯停机信号**：`while !enabled` 循环里 `select!` 同时等「启用意图」与 `global_stop`（`lib.rs:515-532`）。否则「先暂停、再停止服务」时网关面任务永不返回 → `tokio::join!`（`lib.rs:456`）永远等不到它：端口已关、进程残留、systemd 仍显示 running。回归：`tests/stop_drain.rs:270`（先暂停再 stopService，断言进程退出）。
- 网关面**自己**异常结束只记 error 并退出该面，不拉动管理面（`lib.rs:563-571`；`447-452`：仅当全局停机已置位才发 `mgmt_stop_tx`）——与管理面的死亡语义（§7）刻意不对称：管理面死了必须全停，网关面死了管理面还要留着报 error/供恢复。
- 边界：bind 失败重试走 `continue` 回循环头（`lib.rs:547`），该分支不经过 `global_stop` 的 select——「恢复中持续 bind 失败 + 停机」时，任务要等 bind 成功才观察到停机（静态推导，暂无回归覆盖；改此状态机先补这条边的停机出口）。

## 4. 停机受理：accepted ≠ requested ≠ exited

`stopService`（`admin/service_control.rs:85-105`）三段式：

1. `managedBy == embedded` → 直接拒绝（`87-91`）：后端与壳同进程，停后端只会让窗口变废；正确动作是关窗口（壳随之优雅停机，§1）。
2. `accept_stop()` **立刻**置位（`94`），回执 `ok / stopping:true / restartHint` 先返回前端——回执只代表**已受理**，不代表进程已退出。
3. spawned 任务 sleep **`STOP_DELAY_MS = 1200`ms**（`admin/service_control.rs:32`）后才 `request_stop()`（`95-99`）：这 1.2s 留给 HTTP 响应写回 + 浏览器渲染，避免页面先断、提示后到。

`request_stop` 被 `stop_task` 观测后广播 `stop_tx`（`lib.rs:337-340`）；外部停机信号走同一广播，且该分支**同步补 `control.request_stop()`**（`lib.rs:334`）让 SSE 立刻收流（§6）。页面从「正在停止」切「已停止」的判据是管理面真的连不上，不是回执（契约见 reference/07 §1.5.1）。

受理窗口内的不变量：`[accept, request]` 这 1.2s 里 `stopping()` 已为 true，但两个面仍完全正常服务（SSE 也还开着，它盯的是 `stop_requested` 而非 `stop_accepted`）；外部信号路径则只置 `stop_requested`、不置 `stop_accepted`——`stopping()` 对两者取或（`service_control.rs:200-202`），页面口径一致。

## 5. 顺序停机与三个排空上限

停机是**网关面先收尾、管理面后排空**（`mgmt_stop` future，`lib.rs:344-364`）：

```
t0  stop_tx=true（页面延迟 1.2s 后 / SIGINT / SIGTERM / 窗口关闭 / 管理面死亡）
t1  网关面 drain ≤10s → mgmt_stop_tx=true
    [t0,t1] 管理面继续在线、RPC 可用、stopping=true；等待上限 12s（从 t0 起算）
t2  mgmt_stop future 完成 → 管理面 axum 优雅停机开始 → 排空 ≤5s
t3  两面 join → 无条件收尾（§8）→ 进程退出
```

| 常量 | 取值 | 位置 | 用途 |
| --- | --- | --- | --- |
| `GATEWAY_DRAIN_TIMEOUT_SECS` | 10s | `lib.rs:218` | 网关面 in-flight 排空上限（长流式响应客户端不主动断）；须小于 systemd `TimeoutStopSec`（默认 90s，`lib.rs:217` 注释） |
| `MGMT_STOP_DEADLINE_SECS` | 12s | `lib.rs:212` | 管理面等网关面收尾的上限，从停机信号起算，与网关 10s 重叠 |
| `MGMT_DRAIN_TIMEOUT_SECS` | 5s | `lib.rs:209`（pub） | 管理面自身排空兜底；回归测试引用该常量设预算 |

- 顺序的意义：管理面在网关面排空期间**继续接受请求**并如实报 `stopping=true`，浏览器才能区分「正在停止」与「已停止」；管理面先关则只看到连不上。回归：`tests/stop_drain.rs:308`（挂一条收不完的网关请求，断言排空期间 `getRuntimeControl` 仍 200 且 stopping=true，最终仍退出）。
- 三个上限都是**兜底**而非常规路径：SSE 长连接已在停机时主动收流（§6），管理面 5s 只防其它异常长连接（`lib.rs:200-208` 注释）；网关 10s 只防客户端不肯断的长流式响应。排空超时**降级不报错**：网关面 warn 后强制结束（`lib.rs:616-622`）；管理面 warn 后按 Ok 收（`lib.rs:416-422`）——只有两面真实的 serve 错误向上传播。最坏路径 ≈ 1.2s + 12s + 5s + 收尾，远小于 systemd 90s，不会被 SIGKILL 抢先。
- **上限只在停机开始后计时**（2026-11-04 修复）：管理面 select 的正常服务分支不设时限（`lib.rs:404-406`）；`mgmt_drain` oneshot（`lib.rs:314`）在 `mgmt_stop` 完成时才触发（`lib.rs:362`），5s 从那一刻起算（`lib.rs:408-414`）。
- 事故模式（回归档案）：把 `timeout(5s)` 套在整个 mgmt server 生命周期外 → 管理面启动 5s 后被掐断、监听释放 → 前端反代（vite proxy / nginx）全 502，而网关面与进程还活着（`tokio::join!` 一直等网关面）→ 进程不退、停机信号也不起作用。回归 `tests/mgmt_lifetime.rs:149`：管理面必须活过 `MGMT_DRAIN_TIMEOUT_SECS + 4` 秒、业务 RPC（getRuntimeControl / getCallLogs / listModelFingerprints）仍 200、网关端口不消失；收尾用 stopService、退出预算 45s（`mgmt_lifetime.rs:142/187-197`）。

## 6. SSE 停机主动收流

axum 优雅停机会等所有连接结束；管理面 SSE（`GET /api/wr/events`）是浏览器长连接，不主动收流就把停机钉死（端口已关、进程残留）。机制（`admin/status.rs:562-632`）：

- 每连接一个任务，三路 `select!`：事件总线 / 1s 心跳 / `stop_requested`（`admin/status.rs:584-611`；订阅 `control.stop_requested_rx()`，`568`）。
- 停机请求置位 → 补发一帧 `service-stopping`（`service_stopping_event("shutdown", ts)`，`admin/status.rs:602-608`）→ break 结束响应体 → 连接关闭 → 优雅停机得以继续。
- 帧由 `EventKind::ServiceStopping` 构造（`gateway/events.rs:29/40/184-189`），**不走 broadcast 总线**、每连接直发；契约 `contracts/events-schema.json:63-72`：语义是「已受理、未退出」，客户端须切「正在停止」态并**取消订阅与自动重连**，进程退出以管理面不可达为准。
- `wait_stop_requested` 把「控制通道被丢弃」也按停机处理（`admin/status.rs:649-658`）——宁可提前收流，不无限等待。watch 等待统一「`borrow_and_update` 先判值、不满足再 `changed().await`」（`lib.rs:476-486`）：`wait_for` 在 await 期间持读锁 → future 非 Send，进不了 spawn/select。
- 回归：`tests/stop_drain.rs:200`（开着 SSE 连接也能退出）、`:239`（流以 service-stopping 帧结尾）。

## 7. 故障可观测：管理面意外结束 = 整进程停机

管理面是进程对外唯一管理通道，带着死掉的管理面继续跑，前端只会看到一串 502 而进程看似正常。守护（`lib.rs:426-437`）：mgmt server future 结束后检查全局停机 watch——仍为 false（说明不是停机流程导致的结束，如 accept 失败）→ error 日志 + `request_stop()` + `stop_tx_guard.send(true)` 拉起整进程停机；正常收尾时 watch 已 true，不触发。该路径 mgmt 结果为 Err → CLI 退出码 1 → `Restart=on-failure` 重新拉起（`packaging/wrouter.service:12-13`），与主动停止的退出码 0 相反。

桌面壳的第二层出口：后端线程把最终结果经 `BackendExit` channel 回传（`desktop/src-tauri/src/backend.rs:65/112-125`）；壳的监视线程收到 `Err` → stderr 留痕 + 弹窗「WRouter 后端已停止」→ 用户确认后 `exit(1)`（`desktop/src-tauri/src/lib.rs:192-209/404-414`）。不留一个所有请求都 502 的空窗口。

## 8. 无条件收尾与退出语义

`tokio::join!` 收齐两面结果后（`lib.rs:456`），**无论是否报错**都执行（`lib.rs:459-464`）：

1. `shutdown_request_logs()`：请求日志队列 flush + shutdown（`gateway/mod.rs:261-264`）；
2. `maintenance_task.abort()`：日志保留维护任务终止（`lib.rs:463`）；
3. `store.close()`：丢弃发送端 → SQLite 写线程排空队列 → `PRAGMA wal_checkpoint(TRUNCATE)` → 关连接（`wr-infra/src/sqlite/engine.rs:70-80/177-183`）。

之后才传播两面错误（`mgmt_result?` / `gateway_result?`，`lib.rs:465-466`）——异常路径下日志与 WAL 也必须落盘。正常停机 CLI 返回 Ok → 退出码 0（`wr-cli/src/main.rs:55-62`）；systemd `Restart=on-failure` 不拉起退出码 0 的进程，「停止服务」= 真的停了。重建指引 `restart_hint()`：systemd → `systemctl --user start wrouter.service`、process → `wr serve`、embedded → 空串（`service_control.rs:64-70`）。
